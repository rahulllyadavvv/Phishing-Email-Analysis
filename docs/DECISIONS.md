# Decisions

## P0.1: Project scaffold

- Build backend: setuptools. Packages found automatically: `phishlens*`, `api*`, `ui*`.
- `api/` and `ui/` get `__init__.py` files so they can be imported as packages.
- Empty directories (`data/`, `scripts/`, `tests/fixtures/`, `samples/`, `quarantine/`,
  `reports/`, `phishlens/reporting/templates/`) each have a `.gitkeep`. `samples/`, `quarantine/`
  and `reports/` are gitignored, so they are only created locally.
- Ruff: line length 100, target py311, rules E/F/W/I/B/UP. Excluded: `autopilot.py` and
  `progress.py` (autopilot tooling, not project code) plus the runtime data folders.
- pytest: `testpaths = ["tests"]`, `asyncio_mode = "auto"`. With zero tests pytest exits with
  code 5 ("no tests collected"). This is the expected result for P0.1.
- No version pins for dependencies yet. Pins can be added once the analysis code needs them.
- `.env.example` has sample local defaults for `REDIS_URL` and `DATABASE_URL`. All secrets are left blank.

## P0.2: Shared data models

- Fixed value sets are `StrEnum`s: `Severity`, `UrlSource`, `IOCType`, `CaseType`, and
  `VerdictLabel` (`clean` / `suspicious` / `malicious`, matching the report badges in PROMPTS.md).
  `IOC.verdict` stays a free `str | None` because reputation services use different words.
- Byte fields (`Attachment.data`, `ParsedEmail.raw_bytes`) use `Field(exclude=True, repr=False)`.
  They never appear in `model_dump()`, JSON output or repr. After a JSON round trip they are `b""`.
- `AnalysisReport.email` reuses `ParsedEmail` rather than a separate summary model. The byte
  exclusion already makes it a summary without raw bytes. `file_info` is an `Attachment`.
- `ParsedEmail.headers` is `list[tuple[str, str]]`, serialized as `[name, value]` pairs.
- `reply_to` is a list of `Address` (Reply-To can hold several addresses). `return_path` and
  `sender` are single optional addresses.
- `Finding.id` is checked against a snake_case regex. `Verdict.total_score` must be 0-100 and
  `confidence` must be 0.0-1.0. `Verdict` is optional on `AnalysisReport` so a partly built report
  can still be valid.
- All models use `extra="forbid"` so typos in field names fail fast. `created_at` defaults to
  the current UTC time.

## P0.3: Config and CLAUDE.md

- API keys (and `PHISHLENS_API_KEY`) are `SecretStr | None` so they never appear in repr, logs or
  `model_dump()`. `CAPE_BASE_URL` is a plain `str | None`, because it is a URL and not a secret.
- `env_ignore_empty=True`: blank values in `.env` (as in `.env.example`) fall back to the defaults.
  This also means `UPLOAD_FILES_TO_VT=` means `false`.
- `TRUSTED_*` lists are comma-separated strings. They are split, stripped and lower-cased into
  `list[str]` (using `NoDecode` so pydantic-settings does not try to parse them as JSON).
- `Settings.is_enabled(service)` / `configured_services()` use a `SERVICE_FIELDS` map
  (virustotal, abusech, google_safebrowsing, urlscan, abuseipdb, hybrid_analysis, cape, llm).
  An unknown service name raises `KeyError`, because that is a programming error.
- `get_settings()` uses `lru_cache(maxsize=1)`. Tests call `get_settings.cache_clear()`.
  `.env` is read relative to the current working directory. `extra="ignore"` so that unrelated
  variables in `.env` do not break startup.
- Rate-limit and cache TTL settings are not added yet. P4.1 will add them to config.
- The CLAUDE.md commands for the API and UI (`uvicorn api.main:app`, `streamlit run ui/app.py`)
  name modules that later phases will create.

## P0.4: Synthetic test fixtures

- The fixtures are generated by `scripts/make_fixtures.py` and committed. The output is
  deterministic (fixed Date, Message-ID, MIME boundaries and zip timestamps).
  `tests/test_make_fixtures.py` checks that the committed files match the generator byte for byte.
- `labels.yaml` is generated from the same table as the fixtures. Each entry has `verdict`
  (`clean` / `suspicious` / `malicious`) and `expected_signals`. The signals are only descriptive
  hints. They are not binding finding IDs, and later phases may map them to real finding IDs.
- Verdict choices: `zip_attachment` is `clean` (an aligned sender and a harmless text file).
  `password_zip`, `tracking_pixel`, `qr_code`, `display_name_trick` and `duplicate_from` are
  `suspicious`. The rest are `malicious` except `clean_newsletter`.
- Real brand domains appear only where the spec requires them: `microsoft.com` in the spoofed
  From, `paypal.com` as link text and `company.com` inside a display name. `zetatech.xyz` is used
  as the spec says. Every link target uses `.example`. Every IP is in a documentation range.
- The encrypted zip uses traditional PKWARE ZipCrypto, written by hand, because `zipfile` cannot
  write encrypted archives. The entry is stored (not compressed) and the fixed header bytes keep
  it deterministic.
- The duplicate `From` fixture uses a `compat32` `Message`, because `EmailMessage` rejects a
  second `From` header.
- The HTML smuggling attachment wraps the Blob / `createObjectURL` / `download` pattern in a
  function that is never called, and it has no `click()`. The embedded data is harmless base64 text.
- The script builds the EICAR string from pieces, so the script file does not contain the full
  signature. It does appear, base64-encoded, in `eicar_attachment.eml`. Local antivirus may flag
  or quarantine that file.
- The QR code is generated with `segno` (pure Python, added to the `dev` extras). `pyyaml` was
  added to the main dependencies because the YAML data files need it.
- Serialization uses LF line endings (the `email` default). Mail clients and editors accept them.

## P1.1: Email loader

- Detection uses only the content. The file extension and `filename` are never trusted, and
  `filename` only appears in error messages.
- `.eml` detection: every line up to the first blank line (checking at most 50 lines / 64 KB) must be
  an RFC 5322 header field or a folded continuation line. There must be at least two fields, and one
  of them must be a common mail header (From, Sender, Reply-To, Subject, Received, Return-Path,
  Message-ID, MIME-Version, Delivered-To). A UTF-8 BOM, leading blank lines and an mbox `From `
  separator line are allowed. If a NUL byte is present, the input is not an email.
- `.msg` detection: the data starts with the OLE signature and `extract_msg.openMsg` opens it as a
  message type that has `asEmailMessage`. Other OLE files (`.doc`, `.xls`, corrupt files, other
  MAPI types without `asEmailMessage`) load as `"file"`.
- Conversion uses extract-msg's own `asEmailMessage()` (headers, plain/HTML bodies, attachments,
  embedded messages), serialized with `email.policy.default`. If a message is recognized but
  conversion fails, the loader raises `MsgConversionError`. It is not silently treated as a file.
- `load_input` must return a 2-tuple, so the missing-transport-headers warning is carried inside
  the converted bytes as the header `X-PhishLens-Parse-Warning: msg_no_transport_headers: ...`.
  The parser (P1.2) should move this header into `ParsedEmail.parse_warnings`.
- Size limit: new setting `MAX_INPUT_SIZE_MB` (float, default 25, must be > 0). Inputs over the
  limit raise `InputTooLargeError`. For paths, the size is checked with `stat()` before the file is read.
  `LoaderError` (a `ValueError`) is the base class for loader errors.
- extract-msg cannot write `.msg` files and no `.msg` fixture exists, so the `.msg` tests mock
  `extract_msg.openMsg`. The corrupt-OLE test uses the real library.

## P1.2: Header and address parsing

- Entry point is `parse_headers(raw: bytes) -> ParsedEmail`. It fills `headers`, the address
  fields, `subject`, `date`, `message_id`, `raw_bytes`, `sha256` and `parse_warnings`. Later
  parser steps fill in the bodies, Received chain and attachments.
- Header values are decoded with `policy.default.header_fetch_parse` on `msg.raw_items()`, so
  duplicates and the original order are kept. Folded values are unfolded. If decoding raises, the
  parser falls back to `email.header.decode_header`, and after that to the raw unfolded text.
- Warnings are `"<code>: <detail>"` strings. The codes are `missing_from`, `empty_from`,
  `multiple_from_headers`, `multiple_from_addresses`, `display_name_contains_email`,
  `header_decode_error` (an exception, or U+FFFD in the decoded text) and `header_defect`
  (defects reported by the `email` package, such as an unknown charset).
- `display_name_contains_email` is checked on From, Sender and Reply-To. It is not raised when the
  address in the display name matches the real address (case-insensitive), because some mail
  clients use the address itself as the display name.
- `from_addrs` holds the addresses from every From header, in order. `sender` and `return_path`
  take the first address. `Return-Path: <>` (null sender) gives `return_path = None`.
- The loader's `X-PhishLens-Parse-Warning` header moves into `parse_warnings` and is removed from
  `headers`.
- `org_domain` uses `tldextract` with the bundled public suffix snapshot
  (`suffix_list_urls=()`, no cache dir), so it never uses the network. Domains without a known
  public suffix (reserved `.example` / `.test`, single labels) fall back to the last two labels.
  IP literals are returned unchanged. `domain` is lowercased. The local part is kept as written.

## P1.3: Received chain

- Entry points: `parse_received(value) -> ReceivedHop` (one header),
  `parse_received_chain(values) -> (chain, warnings)` (values in header order, newest first) and
  `received_chain_from_headers(ParsedEmail.headers)`. The chain is returned **oldest first**. The
  `ReceivedHop` docstring in `models.py` said "newest first" and was changed to match. Filling
  `ParsedEmail.received_chain` is left to the parser step that puts the parts together.
- The header is split at the last `;` into the clauses and the timestamp. Clause keywords (`from`,
  `by`, `via`, `with`, `id`, `for`) only count outside parentheses, so a comment such as
  "(Authenticated by ...)" does not start a `by` clause. `from_host` is the HELO name (the first
  token after `from`). It is `None` when the HELO is a bracketed IP literal.
- The IP is taken only from the `from` clause. Bracketed parts (`[1.2.3.4]`, `[IPv6:...]`) come
  first, then any bare token that parses as an IP. IPv4-mapped IPv6 addresses are turned into
  IPv4. Timestamps with no zone are treated as UTC so they can be compared.
- Warning codes: `received_no_ip` (every hop with no parsable IP, including `by`-only local
  hops) and `received_out_of_order` (a hop's timestamp is strictly earlier than the timestamp of
  the last earlier hop that had one). There is no clock-skew tolerance.
- `originating_external_ip(chain, trusted_internal_hosts)` returns an IP string. It walks from
  the newest hop back towards the sender and returns the first hop that is not internal. A hop
  is internal when its IP is private, loopback, link-local, multicast, reserved, unspecified or
  CGNAT, or when its IP or `from` host matches `trusted_internal_hosts`. That list can hold IPs,
  CIDRs, host names or domains, and a domain also matches its subdomains. Walking from the
  newest hop means a forged older hop cannot become the result. The result is the IP that handed
  the message to our infrastructure. Without trust config, a public IP on our own MX would be
  returned.
- Documentation ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24, 2001:db8::/32) count as
  **external**, even though Python's `ipaddress` calls them private. This is because the
  synthetic fixtures use them in place of public IPs.

## P1.4: Bodies and URL extraction

- Entry points in `phishlens/parser/body.py`: `parse_bodies(raw) -> BodyParts` (text body, HTML
  body, URLs, warnings), plus `extract_bodies(msg)`, `html_to_text(html)`, `extract_urls(text,
  html)` and `normalize_url(url)`. Filling `ParsedEmail.text_body` / `html_body` / `urls` is left
  to the parser step that puts the parts together (same as P1.3).
- Body parts: every `text/plain` / `text/html` leaf that is not `Content-Disposition: attachment`.
  Nested `message/*` parts are skipped (they become `nested_emails` in P1.5). Several parts of the
  same type are joined with a newline. A missing charset means UTF-8. An unknown charset falls
  back to UTF-8 (`unknown_charset` warning). Bytes that are invalid in the charset are replaced
  (`charset_decode_error` warning). MIME defects are reported as `mime_defect` warnings.
- The text body is derived from the HTML only when there is no non-empty plain text part.
  `script`, `style`, `noscript`, `template` and `head` are dropped. The HTML is parsed with the
  stdlib `html.parser` backend (no lxml dependency).
- "Keep all sources for each URL": `UrlRef` has one `source`, so deduplication is by
  `(url, source, visible_text)`. A URL found in both the text body and an href gives two
  `UrlRef`s. The same href with different link texts also gives one ref per text, so mismatches
  are never hidden.
- Added `UrlSource.META_REFRESH` for `<meta http-equiv="refresh">` targets. `img`, `script` and
  `iframe` src map to `HTML_SRC`. `a` and `area` href map to `HTML_HREF`, and their visible text is
  the link text with whitespace collapsed (`None` if the link has no text, e.g. an image link).
- Normalization: control characters and whitespace are removed, and `www.` links get `http://`.
  Scheme and host are lowercased (userinfo, path and query are kept as written), trailing dots on
  the host and default ports are removed, and an empty path becomes `/`. Only absolute `http`,
  `https` and `ftp` URLs are kept. `mailto:`, `javascript:`, `data:`, `cid:` and relative URLs are
  dropped (`<base href>` is not applied). IDN hosts are kept in Unicode.
- Text-body regex: `http(s)://`, `ftp://` or `www.` up to whitespace, quotes or angle brackets.
  Trailing sentence punctuation and unbalanced closing brackets are stripped.

## P1.5: Attachment and nested email extraction

- Entry points: `phishlens/parser/attachments.py` has `extract_attachments(msg) -> ExtractedParts`
  (attachments, inline images, nested messages, warnings) and `make_attachment(filename, data,
  ...)`, which hashes md5/sha1/sha256 so it can be reused for files unpacked in Phase 6.
  `phishlens.parser.parse_email(raw_bytes) -> ParsedEmail` puts headers, Received chain, bodies,
  URLs and attachments together. The P1.3/P1.4 fields (`received_chain`, `text_body`,
  `html_body`, `urls`) are filled here. `auth_results_headers` is filled with the values of every
  `Authentication-Results` header in order (`ARC-Authentication-Results` is not included).
- Classification of leaf parts: `text/plain` / `text/html` without `Content-Disposition:
  attachment` are bodies (same rule as `body.py`) and are skipped. `image/*` parts that are not
  `attachment` (inline, or no disposition, e.g. `multipart/related` images) go to
  `inline_images`. `message/rfc822` and `message/global` become `nested_emails`. Every other
  leaf part, including inline non-image parts and other `message/*` types, is an attachment.
  Nested emails are not also listed as attachments.
- Filename: `Content-Disposition` filename, then the `Content-Type` `name` parameter (RFC 2231 /
  encoded words decoded, whitespace collapsed, otherwise kept as declared so double extensions
  stay visible). If there is none, it becomes `part-<n><ext>`, where `n` is the 1-based index of
  the non-body leaf part, and the extension is guessed from the MIME type (`.eml` for messages,
  `.bin` if unknown).
- `declared_type` is the part's `Content-Type`. `detected_type` stays `None` (content sniffing
  comes later). `depth` stays 0 and `parent` stays `None` for MIME attachments. Those fields
  describe archive nesting (Phase 6). Attachments of a nested email are in that nested
  `ParsedEmail`, not in the outer one.
- Nested emails: the standard library does not keep the original bytes of a `message/rfc822`
  part, so the inner message is re-serialized (`policy.default` with no header refolding) and
  parsed from those bytes. Its `sha256` / `raw_bytes` are for the re-serialized form, which may
  differ from the original bytes in line endings. The top-level email is depth 0, and nested
  emails are parsed down to depth 3 (`MAX_NESTED_DEPTH`). A message below that is kept as a
  plain `message/rfc822` attachment of the depth-3 email, with a `nested_depth_exceeded`
  warning.
- A payload that cannot be transfer-decoded gives an empty attachment and an
  `attachment_decode_error` warning. An unexpected error during the walk is recorded as
  `attachment_extract_error`, and the parts found so far are kept.

## P2.1: DNS helper and trusted Authentication-Results

- `phishlens/enrichment/dns.py`: `resolve(name, rdtype)` plus `txt()`, `mx()` and `a()` helpers.
  They return a `DnsResult` (`records`, `error`, `cached`) and never raise. Error codes:
  `nxdomain`, `no_answer`, `timeout`, `no_nameservers`, `unsupported_type`, or
  `error: <type>: <message>`. Names are lowercased and the trailing dot is removed before lookup
  and caching.
- Record formats: TXT character-strings are joined with no separator (as SPF/DMARC expect), MX
  records are `"<preference> <exchange>"` sorted by preference, A records are dotted IPs.
  (P2.2 added AAAA, as IP strings, and PTR, as host names without the trailing dot.)
- Caching: an in-memory dict, plus a SQLite table (`dns_cache`) in `DNS_CACHE_PATH` when
  `DNS_SQLITE_CACHE=true`. Both use `DNS_CACHE_TTL_SECONDS`; `0` turns caching off. Only
  definitive answers are cached (records, `nxdomain`, `no_answer`). Timeouts and other errors are
  retried next time. A broken or unreadable SQLite file is ignored, so lookups still work. SQLite
  calls are synchronous. They are small local operations, so they are not moved to a thread.
- DNS is not rate limited. The per-service rate limiting in P4.1 is for HTTP APIs.
- Tests replace the private `_query(name, rdtype, timeout)` coroutine with `monkeypatch`.
- `phishlens/analyzers/header.py` (module name `header`): every `Authentication-Results` value is
  parsed with `authres` (`parse_value`), and the authserv-id is compared, lowercased, against
  `TRUSTED_AUTHSERV_IDS`. `raw["auth_results"]` lists every header (`raw`, `authserv_id`,
  `results`, `trusted`, `parse_error`). `raw["trusted_auth_results"]` has the method results
  (`method`, `result`, `properties` keyed `"type.name"`, e.g. `smtp.mailfrom`) from trusted
  headers only. Later SPF/DKIM/DMARC steps should read only these.
- Empty `TRUSTED_AUTHSERV_IDS`: the forgery check is skipped (missing configuration means
  skipped, per CLAUDE.md), because otherwise every email would get a
  `forged_auth_results_header` finding. All headers are then marked untrusted and
  `raw["trusted_authserv_ids_configured"]` is `False`.
- An Authentication-Results header that `authres` cannot parse has no authserv-id, so it counts as
  untrusted. When a trust list is configured it is flagged as `forged_auth_results_header`, with
  the parse error kept in `raw`. One finding is produced per untrusted header.
- `Finding.score` is left at 0. Scores come from `weights.yaml` in P10.1 (severity fallback: medium
  = 15).

## P2.2: SPF verification

- pyspf does its own synchronous DNS through the module-level `spf.DNSLookup`.
  `phishlens/enrichment/spf_check.py` replaces it with a function that sends each query back to the
  event loop (`asyncio.run_coroutine_threadsafe`) and answers it with our cached DNS helper, while
  `check_spf` runs pyspf in a worker thread (`asyncio.to_thread`). So SPF lookups share the cache
  and are mocked like all other DNS. The loop is passed in a `ContextVar`. Outside `check_spf` the
  replacement falls back to pyspf's own resolver, so other pyspf users are not affected.
- The DNS helper gained AAAA (for `a`/`mx` with an IPv6 sender) and PTR (for `ptr` and macros).
  Other types (the obsolete type 99 SPF record, only queried in pyspf's harsh mode) return no
  answer.
- The SPF bridge lives in `enrichment/` rather than in the analyzer, because it makes DNS calls.
- pyspf runs with default strictness and a 20 s total query time (RFC 7208 4.6.4). DNS
  timeouts/errors -> `temperror`, broken records -> `permerror`, an unexpected exception ->
  `temperror` with the error text in `explanation`.
- Inputs: the IP is `originating_external_ip(received_chain, TRUSTED_INTERNAL_HOSTS)`. MAIL FROM is
  the Return-Path address. A null Return-Path (`<>`, bounces) parses to `None`, so SPF checks the
  HELO identity (`postmaster@<helo>`), as RFC 7208 2.4 says. HELO is the `from` host of the newest
  hop with that IP, used only if it looks like a host name (not `[ip]` or `unknown`).
- Nothing to evaluate: `raw["spf"] = {"result": None, "skipped_reason": ...}` with
  `no_originating_ip` or `no_identity`, and no finding. Trusted Authentication-Results SPF results
  are not used as a fallback here; P2.4 can decide whether to use them.
- `raw["spf"]` when evaluated: `result`, `ip`, `identity` (`mailfrom`/`helo`), `domain` (the
  SPF-authenticated domain), `mail_from`, `helo`, `explanation`.
- Findings (severity, score from `weights.yaml` later): `spf_fail` high, `spf_softfail` medium,
  `spf_none` low, `spf_error` low (both temperror and permerror). `pass` and `neutral` give no
  finding.

## P2.3: DKIM verification and signature quality

- dkimpy needs a single DNS lookup per signature (the `<s>._domainkey.<d>` TXT key), so
  `phishlens/enrichment/dkim_check.py` fetches the key with the async DNS helper first and hands
  it to dkimpy through its `dnsfunc` argument. No thread and no dkimpy resolver are used (unlike
  SPF, which needs many lookups in the middle of evaluation). The key is also checked with
  `dkim.evaluate_pk` beforehand, so a broken key is told apart from a bad signature.
- Each signature is verified separately (`verify_headerprep(idx)` + `verify_sig`) and gets a
  status: `pass`; `fail` (body hash mismatch or signature mismatch); `permerror` (malformed tags,
  no key record, bad or too-small key, under 1024 bits per RFC 8301); `temperror` (DNS timeout or
  failure while fetching the key); `expired` (dkimpy refuses signatures whose `x=` is past).
- Tags (`d`, `s`, `a`, `h`, `l`, `t`, `x`) are read with dkimpy's own `parse_tag_value`
  independently of verification, so they are recorded even when verification fails.
- `raw["dkim"]`: `signatures` (one dict per signature, header order, with `valid`) and
  `delivery_time`. If DKIM-Signature headers exist but `raw_bytes` is empty (a `ParsedEmail` built
  in code), DKIM is skipped with `skipped_reason: no_raw_message`.
- One finding per ID, with the affected signatures listed in `evidence["signatures"]`, so the
  scorer never counts the same problem twice for one email:
  - `dkim_none` (low): no DKIM-Signature header.
  - `dkim_invalid`: signatures with `fail` or `permerror`. Medium when no signature passes, low
    when another signature on the message passes. `temperror` gives no finding: a DNS problem on
    our side is not evidence against the sender.
  - Quality findings are checked on valid signatures only, because an invalid signature
    authenticates nothing anyway: `dkim_body_length_tag` (medium, `l=` present),
    `dkim_unsigned_critical_headers` (medium, From/Subject/To missing from `h=`).
  - `dkim_expired_or_old` (medium): an `expired` signature, or a valid one whose `t=` is more than
    `DKIM_MAX_AGE_DAYS` (default 7) before delivery. Delivery time is the newest Received
    timestamp, else `Date`, else now. Measuring at delivery rather than now means old archived
    mail is not flagged as a replay. Caveat: dkimpy's `x=` check is against the current time, so
    an archived message whose signature has since expired is reported as `expired`.
- `cryptography` is added to the dev dependencies because the tests generate RSA keys with it
  (it is already installed as a dependency of msoffcrypto-tool).

## P2.4: DMARC policy and alignment

- `phishlens/enrichment/dmarc_check.py` finds the record at `_dmarc.<From domain>`, then at
  `_dmarc.<org domain>` (RFC 7489 6.6.3), through the DNS helper. The effective `policy` is `sp`
  (default `p`) when the record came from the organizational domain, else `p`. Records are parsed
  by hand (a simple tag list), not with `checkdmarc`, which would do its own DNS lookups.
- Lenient parsing, each fallback noted in `warnings`: invalid or missing `p=` -> `none`, invalid
  `sp=` -> use `p=`, invalid `adkim`/`aspf` -> relaxed, invalid `pct` -> 100. More than one
  DMARC record means no policy (RFC 7489). A DNS timeout or failure sets `error`, and the DMARC
  result becomes `temperror`.
- Alignment is computed from our own SPF (P2.2) and DKIM (P2.3) results, never from
  Authentication-Results: relaxed = same organizational domain (`parser.headers.org_domain`),
  strict = exact domain. `dkim_aligned` counts only signatures with status `pass`. For SPF the
  authenticated domain is the MAIL FROM domain, or the HELO name for a null MAIL FROM (RFC 7489
  3.1.2). Trusted Authentication-Results are not used as a fallback when our own SPF/DKIM could
  not run. That keeps a single source of truth. We can revisit if real samples show gaps.
- Only the first From address is used. Multiple From headers are handled in P2.5.
- DMARC `result`: `pass`/`fail` when a record exists, `none` without one, `temperror` on a DNS
  error. `raw["dmarc"]` holds the record fields plus `result`, `spf_aligned`, `dkim_aligned`,
  `dmarc_pass` and `auth_but_unaligned`. `raw["auth_summary"]` has one row per mechanism
  (`mechanism`, `result`, `domain`, `aligned`): SPF, each DKIM signature (or a `none` row), and
  DMARC. For SPF/DKIM rows `aligned` is domain alignment, whatever the result.
- Deviation from the plan: `spf_pass_unaligned` and `dkim_pass_unaligned` (high) are raised only
  when DMARC does not pass. Ordinary ESP mail has SPF passing for the ESP's bounce domain while
  DKIM aligns with From. Flagging that high would hit most legitimate bulk mail.
- Findings: `auth_but_unaligned` (critical; SPF or DKIM passed but DMARC did not, with or
  without a DMARC record), `spf_pass_unaligned` / `dkim_pass_unaligned` (high), `dmarc_fail`
  (high; record exists and no aligned pass), `dmarc_none_record` (low; no record and no DNS
  error) and `dmarc_policy_none` (low; effective policy is none). `dmarc_none_record` and
  `dmarc_policy_none` describe the From domain's setup rather than the message, so both stay
  low. The final weighting comes from `weights.yaml` in P10.1. On `temperror` no DMARC policy
  finding is raised, but the alignment findings still are, because they need no record.

## P2.5: ARC, ESPs and header anomalies

- `phishlens/data_loader.py` is created here, earlier than P3.1, because `data/esp_domains.yaml`
  is needed now. Each file is read once (`functools.cache`) and validated with pydantic (frozen
  models, `extra="forbid"`), so a broken data file fails loudly. `clear_cache()` resets it. P3.1
  adds its files to the same module.
- `esp_domains.yaml`: `esps: [{name, domains}]`. A domain matches an ESP when it equals one of
  its domains or is a subdomain of one. `esp_unaligned` (medium) fires when DMARC does not pass
  and every passing SPF/DKIM domain belongs to an ESP. It names the ESPs. It comes on top of
  `auth_but_unaligned`, adding context: phishers often send through bulk email services.
- ARC (`verify_arc` in `dkim_check.py`): as with DKIM, the keys named by every ARC-Seal and
  ARC-Message-Signature are fetched first through the DNS helper and served to dkimpy's
  `ARC.verify` from a dict. A key that cannot be fetched goes into `key_errors`, and that
  signature fails. `chain` is `pass`, `fail` (including dkimpy's `None`, meaning an earlier
  sealer reported a failure) or `none`. `sealer` is the ARC-Seal `d=` of the newest instance, the
  last intermediary before us.
- Trusted: `chain == pass` and the sealer equals, or is a subdomain of, a `TRUSTED_ARC_SEALERS`
  entry. When trusted, the findings a forwarder typically causes (`spf_fail`, `spf_softfail`,
  `dkim_invalid`, `dmarc_fail`) are set to low, with `evidence["downgraded_by"]`.
- Beyond the plan: forwarders usually rewrite the envelope sender, so SPF passes unaligned and
  legitimate forwarded mail would otherwise show `auth_but_unaligned` as critical. So when the
  trusted sealer's own ARC-Authentication-Results (newest instance) recorded `dmarc=pass` for
  the original message, `spf_pass_unaligned`, `dkim_pass_unaligned`, `auth_but_unaligned` and
  `esp_unaligned` are downgraded too. That is the use ARC is designed for (RFC 8617). Without
  that recorded pass they stay as they are. `arc_trusted_forward` (info) is added only when
  something was actually downgraded.
- ARC is skipped without `raw_bytes` (`skipped_reason: no_raw_message`), like DKIM.
- Parser warnings -> findings (one per ID, with the warnings in `evidence["warnings"]`):
  `multiple_from_headers` -> `multiple_from_headers` (high); `display_name_contains_email` ->
  `display_name_contains_address` (medium); `received_out_of_order` and `received_parse_error` ->
  `received_chain_anomaly` (low). `received_no_ip` is not mapped, because internal hops often
  have no IP. `multiple_from_addresses` is not mapped either, since it is not in the plan. We can
  add it later.
- `raw["header_verdict"] = {verdict, risk, reason}`, checked in this order:
  1. DMARC not evaluated (no From) -> `unknown`.
  2. `dmarc_pass` -> `ok` / low.
  3. Trusted ARC, and either not `auth_but_unaligned` or original `dmarc=pass` ->
     `likely_forward` / low.
  4. `auth_but_unaligned` -> `spoofing` / critical.
  5. DMARC `temperror` -> `unknown`.
  6. No DMARC record, or effective policy `none` -> `fail_policy_none` / critical (nothing
     stopped delivery; "higher if p=none let it through").
  7. Otherwise `fail` / high.

## P3.1: Reference data

- `phishlens/data_loader.py` (started in P2.5) now loads `brand_registry.yaml`, `free_webmail.yaml`,
  `risky_tlds.yaml` and `shorteners.yaml`, each validated by a frozen pydantic model and cached.
  Domain and keyword lists share the `Names` type (lowercased, trailing dot stripped, blanks

- Some free webmail domains are also legitimate brand domains (gmail.com for Google;

## P3.2: Domain consistency and display-name spoofing

- `phishlens/analyzers/domain.py`, module name `domain`. The Sender header is shown in
  `raw["domain_table"]` but produces no finding (the plan lists none for it).
- Comparisons use organizational domains, so `bounce@mail.company.example` matches
  `company.example`.
- `returnpath_mismatch` is low, or info when the Return-Path is a known ESP (normal for bulk

- `replyto_mismatch` (medium) fires when a Reply-To address's org domain differs from From.

  outlook.com), because anyone can register there. One finding per brand mentioned.
- `find_brand_mentions(text)` is public and reused by later steps (subject, body). Keywords match
  as whole words, with flexible separators between the words of a phrase (`office-365` matches

  also refreshes them. The `organization` section counts as one more brand when it has a name
  and domains.

## P3.3: Lookalike domain detection

- `check_lookalike(domain) -> list[LookalikeMatch]` lives in `phishlens/analyzers/domain.py`, as
  the plan says. The URL analyzer will import it from there. It accepts ASCII, punycode or Unicode
  input. It returns nothing for any (subdomain of a) brand's legitimate domain, and at most one
  match per brand, the strongest by kind: homoglyph > typosquat > combosquat > tld_swap >
  brand_in_subdomain.
- Homoglyphs, digits and IDN: both sides are reduced to a "skeleton" (NFKC, lowercase, then the
  single-character map, then multi-character sequences such as `rn`->`m`) from
  `data/confusables.yaml`, a small hand-made subset of Unicode confusables for Latin, Cyrillic,
  Greek and digits. `i`, `1`, `l` and `|` all map to `l`, since they look alike. Punycode labels
  are decoded with Python's `idna` codec. A label that fails to decode is kept as it is.
- The domain is split into subdomain, registered label and suffix with `parser.headers.org_domain`
  (offline tldextract, with its last-two-labels fallback for `.example`/`.test`).
- Typos: Damerau-Levenshtein (rapidfuzz) on skeletons, only for brand labels of at least 6
  characters (distance 1; 2 from 9 characters on). Shorter labels (apple, adobe, ups) matched
  ordinary words too often (`apply.com`), so they are caught only as homoglyphs or whole tokens.
- Combosquatting: a hyphen or underscore token that equals, or is a homoglyph or typo of, the
  brand label (`micros0ft-support`). Also the brand label appearing inside the label without a
  separator, for labels of at least 6 characters (so `pineapple` is not Apple).
- `brand_in_subdomain` (`paypal.com.account-check.example`) is an extra kind beyond the plan's
  list, because it is a common phishing pattern. It is reported inside `lookalike_domain`.
- `generic_labels` in `brand_registry.yaml` (office, live, outlook, chase, zoom, ...) are brand
  labels that are everyday words. They match only as homoglyphs of the whole label (`0ffice.com`).
  Accepted trade-off: `outlook-verify.com` is no longer flagged by the lookalike check. Brand
  keywords in display names and bodies still catch most of these.
- A known limit: TLD swaps flag country versions of global brands that the registry does not list
  (for example `amazon.fr`). The fix is to add those domains to the registry.
- Findings, per unique sender domain (From, Return-Path, Reply-To, Sender, with the roles
  listed): `lookalike_domain` (high; all matches in evidence) and `punycode_domain` (medium, or
  high when the domain is also a lookalike). `raw["lookalikes"]` maps each domain to its matches.

## P3.4: Identity binding

- `analyze(email, context=None)`: `context` maps module names to earlier `AnalyzerResult`s. The
  pipeline (P10) will pass `{"header": ...}`. The analyzer contract still holds, because
  `analyze(email)` works on its own.
- Sender identity (`sender_identity`): the first From domain. `authenticated` is taken from the
  header analyzer's `auth_summary` DMARC row (`aligned`, i.e. DMARC passed). It is `None` when no
  header result is available.
- Claims (`ClaimedBrand`, one per brand, listing its sources): From display names
  (`find_brand_mentions`), lookalike matches for any sender domain (`raw["lookalikes"]`), and the
  subject. The tone analyzer will call `bind_identity` with `"body"` claims later.
- `bind_identity(claimed_brands, identity, *, lookalike_domains, new_domains)`. The sender *is*
  the brand when its domain is (a subdomain of) a legitimate brand domain, is not free webmail,
  and is not known to be unauthenticated. Otherwise it produces `brand_impersonation`:
  - critical when the sender domain is a lookalike or newly registered (`raw["new_domains"]`,
    filled by P3.5);
  - medium when the brand was claimed only in the subject or body (weak claims: a newsletter
    may mention a brand);
  - high otherwise.
- Using a brand's real domain without authenticating (fixture 2: From microsoft.com, DMARC not
  aligned) is impersonation. With unknown authentication (no header context) it is not flagged,
  to avoid false positives.
- `raw["identity"]` records the sender domain, whether it authenticated, and the claimed brands
  with their sources.

## P3.5: Domain age and MX

- `phishlens/enrichment/rdap.py` is a minimal RDAP client: `GET https://rdap.org/domain/<domain>`
  with httpx, following the bootstrap redirect to the registry. It reads the `registration` and
  `expiration` events and the registrar name (vCard `fn`, else the handle). It never raises.
  Status is `ok`, `not_found` (HTTP 404), `reserved` or `error`. `ok` and `not_found` are cached in
  memory for `RDAP_CACHE_TTL_SECONDS` (default 1 day; `0` disables); errors are retried. New
  settings: `RDAP_TIMEOUT_SECONDS` (10) and `RDAP_CACHE_TTL_SECONDS`. P4.1 moves this onto the
  shared base client (rate limiting, persistent cache).
- Reserved names (`.example`, `.test`, `.invalid`, `.localhost`, `.local`, and
  `example.com/net/org`) are never sent to RDAP. They get status `reserved` and no finding.
- Only registered (organizational) domains are looked up, deduplicated across From, Return-Path
  and Reply-To. Sender is not looked up, following the plan.
- Age is measured at delivery time (`parser.received.delivery_time`: newest Received timestamp,
  else Date, else now), so old mail analyzed later is judged by its age when it arrived.
  `delivery_time` moved there from the header analyzer, which now uses it too. A registration
  date after delivery (the domain changed hands since) gives no finding.
- Findings, one per domain for the youngest bucket that applies: `domain_age_under_7_days`
  (critical), `domain_age_under_30_days` (high), `domain_age_under_180_days` (low). Domains under
  30 days old go into `raw["new_domains"]`, which makes `brand_impersonation` critical.
  `raw["domain_age"]` holds the RDAP data and `age_days` for every domain. An RDAP failure is
  recorded in `AnalyzerResult.errors` (`rdap: <domain>: <error>`), never as a finding.
- MX follows RFC 5321/7505: `from_domain_no_mx` (medium) fires when the From domain has no MX
  and no A record (implicit MX), or publishes a null MX (`0 .`). Mail to a domain with an A
  record but no MX is still deliverable, and many sending subdomains are set up that way. DNS
  errors other than NXDOMAIN/no answer go into `errors`. `raw["mx"]` shows what was found.
- The async checks (domain age, MX) run concurrently after the sync ones. Identity binding runs
  last, because it needs `raw["new_domains"]`.

## P4.1: Base client, cache and rate limiting

Plan reviewed and approved before building.

- `EnrichmentResult` / `EnrichmentStatus` live in `phishlens/models.py`, because reports and the
  API will carry them. There is one extra field beyond the plan: `error` (a message with secrets
  removed).
- `phishlens/enrichment/base.py`, `BaseClient`: subclasses set `service` (the settings name) and
  implement lookups as `cached_lookup(kind, query, fetch)`. `kind` separates lookup types in the
  cache key (`service:kind:normalized query`), and `normalize()` is per service. `cached_lookup`
  never raises: any exception becomes status `error`. A missing key returns `not_configured`
  before any cache or network access. `requires_key = False` for keyless services (RDAP).
- `request()`: every attempt first takes a rate-limit token. 429, 5xx and `httpx.TransportError`
  (timeouts, connection errors) are retried up to `ENRICHMENT_MAX_RETRIES` times. The wait is
  `Retry-After` when it is given in seconds (capped at 60 s), else 1 s * 2^attempt + up to
  0.5 s jitter. Other statuses (including 4xx) go back to the caller. When all attempts fail,
  `EnrichmentError("<problem> (after N attempts)")` is raised.
- Rate limiting: one token bucket per service per process (`get_limiter`), starting full. It has
  no lock: `acquire` takes a token first (going negative to queue) and then sleeps, so there is no
  `await` between check and update, and it works across event loops (each pytest test has its own).
  Limits: `ENRICHMENT_RATE_LIMITS=service=count/seconds,...` over the defaults in `config.py`
  (VirusTotal 4/60, AbuseIPDB 1000/86400, Hybrid Analysis 5/60, urlscan 60/60, RDAP 1/1,
  abuse.ch, Safe Browsing and CAPE 10/1). Unknown services get 1/1.
- Cache: in memory plus a SQLite table `enrichment_cache` in `ENRICHMENT_CACHE_PATH` (a separate
  file from the DNS cache). The SQLite part can be turned off with `ENRICHMENT_CACHE=false`. Only
  the normalized result JSON is stored, never raw responses. The TTL is
  `ENRICHMENT_CACHE_TTL=service=seconds,...` (default 86400; 0 disables). `error` and
  `not_configured` are never cached. A broken or unreadable cache file is ignored, as with DNS.
- Secrets: `Settings.secret_values()` lists every configured `SecretStr`. Every error message is
  scrubbed of them (`redact`) before it is stored or logged, which covers keys in URLs
  (Safe Browsing `?key=`). Retry and failure log lines contain the service name, status and
  attempt count, never a URL.
- RDAP now uses `RdapClient(BaseClient)` (`service="rdap"`, no key). Its `EnrichmentResult` has
  status `unknown` (RDAP gives registration data, not a verdict) and the data in `details`
  (`rdap: ok|not_found`, registered, expires, registrar). `lookup_domain()` still returns
  `RdapResult`, so the domain analyzer did not change. `RDAP_TIMEOUT_SECONDS` and
  `RDAP_CACHE_TTL_SECONDS` were removed in favour of the generic `ENRICHMENT_*` settings.
- Tests: an autouse fixture in `tests/conftest.py` gives every test its own cache file, empty
  caches and limiters, and replaces `base._sleep` with a recorder, so retries and rate limits
  never really wait.

## P4.2: VirusTotal client

- `VirusTotalClient` (`phishlens/enrichment/virustotal.py`) has `url`, `file` (MD5/SHA-1/SHA-256),
  `domain` and `ip` lookups through `cached_lookup`, plus `upload_file`. The key goes in the
  `x-apikey` header only.
- URL id = unpadded base64url of the URL as given (only surrounding whitespace is stripped). VT
  canonicalizes URLs itself, and changing the case of a path could change the identity.
  Hashes and domains are lowercased.
- Status mapping from `last_analysis_stats`: malicious when `malicious >= VT_MALICIOUS_THRESHOLD`
  (new setting, default 3); suspicious when any `malicious` or `suspicious` vote is below that;
  clean when engines ran with no such votes; unknown when there are no engine results, or on
  HTTP 404 (not in VT, `details.found = False`; this is cached like any definitive answer).
  `detections` = malicious votes, `total_engines` = the sum of all counts.
- `details` keeps the stats, reputation, `last_analysis_date` and a few fields per type (URL: final
  URL, title, categories; file: name, type, size; domain: categories, creation date,
  registrar; IP: country, AS owner, network). Links go to the VT GUI (`/gui/url|file|domain|
  ip-address/...`).
- Upload: only when `UPLOAD_FILES_TO_VT=true` (CLAUDE.md safety rule). Otherwise it returns
  `not_configured` with a reason and makes no network call. Files over 32 MB are refused (they
  would need VT's separate `upload_url` flow). An upload returns status `unknown` with the
  `analysis_id`, because the verdict comes later from a `file` hash lookup. Uploads are not
  cached.
- 401/403 and other client errors become `error` (`HTTP <code>`). A 429 goes through the base
  client's retries; a daily quota that is still exhausted ends as `HTTP 429 (after N attempts)`.

## P4.3: abuse.ch and Google Safe Browsing

- Blocklist semantics: URLhaus, MalwareBazaar, ThreatFox and Safe Browsing only know bad things.
  A hit is `malicious` (ThreatFox: `suspicious` when the highest `confidence_level` is below
  50). "Not listed" is `unknown`, never `clean`, so the P4.5 lookup order still goes on to
  VirusTotal for it.
- `AbuseChClient` (`service="abusech"`): one `ABUSECH_API_KEY` sent as the `Auth-Key` header to
  all three APIs. `urlhaus_url` (form `url=`), `malwarebazaar_hash` (form
  `query=get_info&hash=`), `threatfox_ioc` (JSON `search_ioc`). Cache kinds are separate
  (`urlhaus_url`, `hash`, `threatfox_ioc`), so the same string can be looked up in two feeds.
  `query_status` values other than ok or not-found (e.g. `unknown_auth_key`, `illegal_hash`)
  become `error` with that status in the message. Links: URLhaus reference, MalwareBazaar
  sample page, ThreatFox IOC page.
- `SafeBrowsingClient` (`service="google_safebrowsing"`): v4 `threatMatches:find` with all four
  threat types on `ANY_PLATFORM`. The key can only be sent as the `?key=` query parameter; the
  base client scrubs it from errors and logs (tested).
- Batching: `BaseClient.batch_lookup` (new, generic) answers cached URLs from the cache,
  removes duplicates after normalization, and sends the rest in chunks of 500. Each URL's
  result is cached on its own. A failed chunk marks every URL in it `error` (not cached), and
  other chunks are unaffected. `url()` is a batch of one.
- The link for a Safe Browsing result is Google's Transparency Report search page for that URL.
- `phishlens.__version__` now comes from the installed package metadata (`0.0.0` when run from a
  source tree that is not installed). It is used as the Safe Browsing `clientVersion`.

## P4.4: urlscan.io and AbuseIPDB

- `UrlscanClient.scan(url)`: first a search for a scan of the same URL (`task.url:"<url>" AND
  date:>now-<URLSCAN_REUSE_DAYS>d`, default 7 days; 0 always submits). If there is none, a
  submission with `URLSCAN_VISIBILITY` (default `unlisted`; validated as public, unlisted or
  private). A failed search falls back to submitting. Reusing a scan saves quota and avoids
  visiting the attacker's page again.
- Polling: `/result/<uuid>/` returns 404 until the scan is done. The first wait is 10 s (urlscan's
  guidance), then ×1.5 up to 15 s per wait, for at most `URLSCAN_MAX_WAIT_SECONDS` (90). A timeout
  is an `error` naming the result page, and is not cached. Waits go through `base._sleep`, so tests
  never really wait.
- Result: `malicious` when `verdicts.overall.malicious`, `suspicious` when the overall score is
  above 0, else `unknown`. Details: uuid, whether a scan was reused, score, categories, brands,
  final URL, redirect chain (task URL + the main document's redirect hops + final URL,
  deduplicated), page title, IP, country, screenshot URL and `login_form`. The screenshot and
  result links may be clickable in reports (CLAUDE.md allows screenshot links).
- `login_form`: urlscan's result JSON has no reliable flag, so urlscan's stored rendered DOM
  (`urlscan.io/dom/<uuid>/`) is fetched and searched for `<input type=password>`. This fetches
  urlscan's copy, never the phishing site. None when the copy is unavailable.
- `AbuseIpdbClient.ip(ip)`: `/api/v2/check` with `maxAgeInDays=90`. Status: malicious from abuse
  confidence 75, suspicious from 25, else clean. A whitelisted IP is always clean. Details:
  score, total reports, ISP, country, usage type, domain, last report. IP reputation is a scored
  database rather than a blocklist, so a low score is `clean` (unlike URLhaus or Safe Browsing).
- Test safety: the tests that assert "no network call" used `@respx.mock(assert_all_called=False)`
  together with module-level `respx.get(...)`. Those routes go to a different router, so those
  tests passed without really intercepting anything. They now use the `respx_mock` fixture with
  `@pytest.mark.respx(assert_all_called=False)`. An autouse `no_network` fixture in
  `tests/conftest.py` also makes any real socket connection or name resolution fail the test.

## P4.5: Sandbox clients and lookup order

- `SandboxReport` lives in `phishlens/models.py`: sandbox, task id, status (`done`, `pending`,
  `error`, `not_configured`), verdict (`EnrichmentStatus` values), score 0-100, and lists of
  processes, network domains, IPs and URLs, dropped SHA-256s, signatures, plus link and error.
- `SandboxClient(BaseClient, ABC)`: `submit(data, filename)` returns a task id, or a
  `SandboxReport` saying why nothing was sent. `get_report(task_id)` never raises and returns
  `pending` while the sandbox works. Both return `not_configured` with no network call when the
  service is not set up. Reports are not cached, because they change until the task finishes.
  Errors are scrubbed of secrets.
- Safety beyond the plan: Hybrid Analysis is a public third party, so CLAUDE.md's "never upload
  files to third parties" rule applies. Submitting also needs
  `UPLOAD_FILES_TO_HYBRID_ANALYSIS=true` (new, default false). Report fetches need only the key.
  CAPE runs whenever `CAPE_BASE_URL` is set, because that is normally your own instance and
  setting the URL is itself the opt-in. New settings: `HYBRID_ANALYSIS_ENVIRONMENT_ID` (160,
  Windows 10 64-bit) and an optional `CAPE_API_TOKEN` (`Authorization: Token ...`).
- Hybrid Analysis (Falcon Sandbox API v2; it requires the `User-Agent: Falcon Sandbox` header):
  `POST /submit/file` returns a `job_id`, then `GET /report/<id>/summary`. Verdict: malicious,
  suspicious, "no specific threat" or whitelisted -> clean, else unknown. Score = `threat_score`.
  `IN_QUEUE`/`IN_PROGRESS` -> pending.
- CAPE (API v2): `tasks/create/file/`, `tasks/view/<id>/` (only `reported` is done; `failed_*`
  is an error), `tasks/get/report/<id>/json/`. Verdict from `malscore` (0-10): malicious from 7,
  suspicious from 4, else clean. Score = malscore × 10.
- `phishlens/enrichment/lookup.py`: `url_reputation(url)` asks Safe Browsing -> URLhaus ->
  VirusTotal. `hash_reputation(sha256)` asks MalwareBazaar -> VirusTotal. The chain stops at the
  first `malicious`; anything else (unknown, error, not_configured) moves on to the next
  service. Every result is returned in order, including `not_configured` ones, so reports show
  what was checked. Because the blocklists never answer `clean` (P4.3), VirusTotal is only
  reached when the earlier services had nothing.

## P5.1: Static URL checks

- `phishlens/analyzers/urls.py` (module `urls`):
  `analyze(email, context=None, extra_urls=None)`. `extra_urls` carries URLs found by other
  analyzers (attachments, QR codes), and the pipeline passes them in. URLs are deduplicated on
  the stripped string. Each row in `raw["urls"]` lists all its sources and visible texts.
- Findings are grouped per ID (one finding per ID, `evidence.urls` lists each URL with its
  details, plus `count`). This matches the DKIM and header findings: the scorer counts a kind of
  problem once per email, and the weights in P10 can use `count` if needed. Severities:
  - high: `link_text_mismatch`, `at_sign_in_url`, `brand_in_unrelated_domain`,
    `data_or_javascript_uri`;
  - medium: `ip_address_url`, `punycode_url` (high when the domain is also a lookalike);
  - low: `url_shortener`, `excessive_subdomains` (more than 3 labels before the registered
    domain), `risky_tld`, `credential_keywords`.
- `link_text_mismatch`: the first domain-looking token in the visible text is compared with the
  link's registered domain (organizational domain, so `www.shop.test` and `mail.shop.test`
  match `shop.test`). Visible text without a domain ("Click here") is not a mismatch.
- `ip_address_url` also catches decimal, hex and octal IP forms (`http://3405803785/`,
  `0xcb.0x0.0x71.0x9`).
- `at_sign_in_url` looks only at the authority (userinfo), not at an `@` in the path or query.
- `credential_keywords` checks the path and query only (the host is covered by the lookalike and
  brand checks). Keywords live in `data/url_keywords.yaml` (CLAUDE.md: no hard-coded tables) and
  match as whole words, so `accountants` does not match `account`.
- `brand_in_unrelated_domain` uses `check_lookalike` from P3.3 on the link host.
- `data/url_allowlist.yaml` (short list of big platforms) sets `allowlisted` on a row. P5.2 will
  skip reputation lookups for those URLs, but static checks still run on them.
- Defanging: `phishlens/ioc/defang.py` is created now (P9.1 reuses it). `hxxp`/`hxxps`/`fxp`
  schemes, `[.]` in hosts, `[@]` in the authority and in emails, and `[:]` after `javascript:`,
  `vbscript:` and `data:`. It is idempotent. Everything this analyzer puts in findings is
  defanged (URLs, visible texts, domains in the lookalike matches). `raw["urls"]` keeps the
  original `url` (needed for reputation lookups and IOC extraction) next to `defanged`.
- Open point for P11/P12: the header and domain analyzers (P2/P3) put raw domains and addresses
  in finding descriptions and evidence. Rather than changing each analyzer, the output layer
  (report, API, UI) should defang those fields when rendering. This is noted here so it is not
  forgotten.

## P5.2: URL reputation

- `analyze(..., reputation=True)`: `reputation=False` gives a static-only run with no network at
  all, for offline use or quick checks.
- Every unique URL that is not allowlisted, uses http/https/ftp and has a host goes through
  `lookup.url_reputation`, concurrently (at most 4 at a time). The per-service rate limiters from
  P4.1 still apply. `data:`/`javascript:` URIs and allowlisted URLs are never sent anywhere.
- urlscan.io is used only for URLs where no reputation service had a verdict (every result is
  unknown, error or not_configured), and for at most `MAX_URLSCAN_PER_EMAIL = 5` URLs per email
  (a mailing with dozens of links would otherwise burn the urlscan quota). urlscan visits the
  page in its own browser; nothing is ever fetched from this host.
- Each row in `raw["urls"]` gets `reputation` (per service: status, detections, engines, cached,
  link, error; the raw query is left out), `reputation_verdict` (the worst status: malicious >
  suspicious > clean > unknown > error > not_configured; `None` when no lookup was made), and,
  after urlscan, a defanged `final_url`, `screenshot_url` and `urlscan_link` (report links;
  CLAUDE.md allows screenshot links to be clickable), plus `login_form`.
- Findings (grouped per ID like P5.1):
  - `url_known_malicious` (critical): any service, urlscan included, says malicious. Evidence
    names the services.
  - `url_suspicious_reputation` (medium): the worst verdict is suspicious.
  - `redirect_to_different_domain` (medium): urlscan's final URL is on another registered domain.
  - `urlscan_login_page_on_unrelated_domain` (high): urlscan found a password field, and the final
    registered domain is neither the From domain nor any brand's legitimate domain. A login page
    on the sender's own site or on paypal.com is normal.
- With no API keys, every URL gets `not_configured` from all four services and the result is still
  complete and valid (tested with the real clients; the `no_network` guard proves nothing was
  sent).

## P6.1: Archive unpacking, identification and filename tricks

Plan reviewed and approved before building.

- Modules: `analyzers/filetype.py` (type detection, filename checks), `analyzers/archives.py`
  (unpacking) and `analyzers/attachments.py` (the analyzer, module name `attachments`).
- Type detection: libmagic when installed, otherwise the signatures and text markers in
  `data/file_types.yaml` (hex values must be quoted in YAML). Zips are refined to OOXML
  document types, and to macro-enabled when they contain `vbaProject.bin`. MIME types map to
  categories (executable, script, archive, disk_image, html (incl. SVG), shortcut, onenote,
  office_macro, document, image, text).
- Unpacking happens entirely in memory: nothing is written to disk or executed, so zip-slip
  paths do not matter. It covers zip (pyzipper: ZipCrypto and AES), 7z (py7zr), tar and
  tar.gz/bz2/xz (links and devices are never followed), single-file gzip, and ISO (pycdlib,
  Joliet names when present). RAR, CAB, IMG and VHD are identified but not unpacked (no pure-Python
  extractor); they are still flagged by type.
- Limits: one `Budget` per email, shared by all its archives (`ARCHIVE_MAX_DEPTH` 3,
  `ARCHIVE_MAX_FILES` 100, `ARCHIVE_MAX_TOTAL_MB` 200, `ARCHIVE_FILE_TIMEOUT_SECONDS` 10 per
  member). Data is decompressed in 64 KB chunks, and every chunk is charged against the budget,
  so a bomb stops as soon as it crosses the limit. py7zr's own in-memory writer silently
  truncates, so a custom `WriterFactory` raises instead. For 7z and ISO the declared sizes are
  also checked up front. Files extracted before a limit is hit are kept. Unpacking runs in
  `asyncio.to_thread`. A top-level attachment is depth 0; archives at `max_depth` are not
  opened (a `depth` limit event).
- Passwords: after each hint word in `data/password_hints.yaml` (text body plus the HTML body's
  text), the first token that is not a stopword or hint word is a candidate. After those,
  `infected` (the analyst convention for shared samples) is tried. Once one password opens an
  archive, it is tried first for the archive's other members. A body password that works gives
  `encrypted_archive_password_in_body`. `infected` gives no finding (it is recorded in
  `raw["archive_events"]`). No working password gives `encrypted_archive_unopened`.
- `type_mismatch` only when the content is a risky category (executable, script, archive, disk
  image, HTML/SVG, shortcut, OneNote, macro Office file) that differs from what the extension
  claims (no extension also counts). Generic declared types such as
  `application/octet-stream` do not cause findings on their own. The declared type is shown in
  the evidence.
- `double_extension`: the last extension is high-risk and the one before it is a decoy (from
  `decoy_extensions`). `rtlo_filename` covers U+202A-202E and U+2066-2069. File names are shown
  with these characters made visible (`<U+202E>`) in rows and evidence (`safe_name`).
  `whitespace_padded_extension`: 3 or more (Unicode) spaces before the final extension, or
  whitespace after it. `high_risk_file_type`: the extension is in `HIGH_RISK_EXTENSIONS`
  (settings; defaults from the plan plus vbe, wsf, vhdx, com, pif, cpl, dll), or the detected
  category's typical extension is.
- Severities: `type_mismatch`, `double_extension`, `rtlo_filename`,
  `encrypted_archive_password_in_body` and `encrypted_archive_unopened` are high;
  `whitespace_padded_extension`, `high_risk_file_type` and `archive_limit_exceeded` are medium.
  Findings are grouped per ID with `evidence.files`, as in the URL analyzer.
- Output: `raw["attachments"]` has one row per file, top-level first, each followed by its
  extracted files (filename, safe_name, parent, depth, declared/detected type, size, md5, sha1,
  sha256, flags). `raw["archive_events"]` and `raw["password_candidates"]` are also recorded. A
  corrupt archive is an entry in `errors` (`unpack: <name>: ...`). An email without attachments
  gives `skipped = True`.

## P6.2: Hash reputation

- `analyze(email, context=None, reputation=True)`: every non-empty file (top-level and unpacked)
  is looked up once per unique SHA-256 with `lookup.hash_reputation` (MalwareBazaar ->
  VirusTotal, stopping at the first malicious result), at most 4 at a time. Empty files are
  skipped: the empty-file hash is meaningless. `reputation=False` means no network at all.
- Each `raw["attachments"]` row gets `reputation` (per service: status, detections, engines,
  cached, link, error), `reputation_verdict` (worst status, or `None` when not looked up) and
  `deep_analysis_skipped`. When that is true, `skip_reason` says why. The later content stages
  (P6.3-P6.5) and the sandbox (P6.6) must skip rows with `deep_analysis_skipped`: the verdict is
  already certain, and analyzing known malware again only costs time and sandbox quota.
  Filename checks (P6.1) have already run for every file and stay.
- `attachment_known_malicious` (critical), one finding listing every such file with the services
  that flagged it, detection counts (`"61/70"` per service with engine counts), malware family
  names (MalwareBazaar `signature`, VirusTotal
  `popular_threat_classification.suggested_threat_label`, which the VT client now keeps in
  `details`) and the report links.
- With no API keys the lookups return `not_configured` without any network call, and the rows
  still carry the per-service results.

## P6.3: Office and RTF static analysis

- `phishlens/analyzers/office.py`: `analyze_office(filename, data, mime, passwords) ->
  OfficeReport` (flags, URLs, info, errors). It never raises. The attachment analyzer runs it,
  in a worker thread, on every file whose detected type is Office (OLE2, OOXML, macro-enabled)
  or RTF, except files marked `deep_analysis_skipped` by hash reputation. Findings are grouped
  per ID; `row["office"]` holds the descriptive info; URLs go to `extracted_urls` with source
  `attachment`, deduplicated.
- Encryption: `msoffcrypto` decrypts in memory with the body password candidates, then Excel's
  built-in `VelvetSweatshop` (malware uses it so the file opens without a prompt). Analysis
  continues on the decrypted bytes. `encrypted_office_document` (medium) records whether it was
  decrypted and with which password source. msoffcrypto's own encrypt/decrypt round trip fails
  on minimal test documents, so encryption is tested with a stand-in `OfficeFile` (the plan
  allows mocking).
- Macros: olevba (`detect_vba_macros`, `detect_xlm_macros`, `analyze_macros`) and mraptor on the
  VBA source. `office_macro_autoexec` (high) needs VBA plus an AutoExec keyword.
  `office_macro_suspicious_calls` (high) needs VBA plus any olevba "Suspicious" keyword; the
  plan's key calls (Shell, CreateObject, URLDownloadToFile, WScript, PowerShell) are listed
  separately as `key_calls`, and mraptor's verdict is included. `xlm_macro` (high) when olevba
  finds Excel 4.0 macros. olevba IOC URLs become extracted URLs. Real olevba is tested on a
  harmless plain-text VBA module; XLM uses a mocked scan result.
- OOXML: every `.rels` part (at most 1 MB) is parsed with ElementTree (the bundled expat
  protects against entity-expansion bombs). External relationships: `attachedTemplate` ->
  `remote_template_injection` (high); oleObject, frame, subDocument, package, external
  workbook links and controls -> `office_external_link` (medium); hyperlinks only produce
  extracted URLs, since links in documents are normal. `embeddings/` parts and OLE
  `\x01Ole10Native` streams are listed in `office.embedded_objects` without a finding (the
  embedded payloads are not extracted as separate files yet).
- RTF: rtfobj lists embedded objects. `rtf_embedded_object` (medium) lists the class names,
  package file names and whether an object is Equation Editor (CVE-2017-11882), so the report
  can call that out. `http(s)` URLs in the RTF text become extracted URLs.
- oletools loggers are silenced (problems come back in `errors`), and pytest ignores the
  pyparsing deprecation warnings raised inside `oletools.olevba`.

## P6.4: PDF, HTML and SVG static analysis

- `phishlens/analyzers/documents.py`: `analyze_pdf(data)` and `analyze_html(data, mime)` return
  the same report shape as the Office analyzer (`OfficeReport`, used here as `ContentReport`,
  now with `qr_urls`). The attachment analyzer picks the analyzer by detected type (Office/RTF,
  PDF, HTML/SVG), runs it in a worker thread, and skips `deep_analysis_skipped` files. Each file
  type's info goes in its own row key (`office`, `pdf`, `html`). URLs found go to
  `extracted_urls` with source `attachment`, and decoded QR codes with source `qr_code`.
- PDF (pypdf, never rendered): every object reachable from the trailer is visited (at most
  50,000 nodes; each indirect reference once), so actions hidden in object streams are found
  too. pypdf decodes obfuscated names such as `/J#61vaScript`.
  - `pdf_javascript` (high): a `/JS` or `/JavaScript` key, or a JavaScript action.
  - `pdf_auto_action` (high): an `/OpenAction` that is an action dictionary, or any `/AA`
    entries (listed as `AA<trigger>:<action>`). An `/OpenAction` that is only a destination
    (`[page /Fit]`) sets the initial view and is not flagged.
  - `pdf_launch_action` (critical): a `/Launch` action; `/F` targets are listed.
  - `pdf_embedded_file` (medium): embedded files, with their names from `reader.attachments`.
    They are not unpacked as separate files yet.
  - `/URI` values become extracted URLs. An encrypted PDF is tried with the empty user password;
    otherwise it is recorded as an error.
  - QR: images on the first 20 pages (at most 50 images) are decoded with `qr.decode_qr`.
- `phishlens/analyzers/qr.py` (shared with P6.5): pyzbar + Pillow. Images over 40 megapixels are
  refused (decompression bombs). Without the zbar library, decoding is skipped and
  `qr_decoding: unavailable` is recorded.
- HTML/SVG (BeautifulSoup `html.parser`, never rendered; script text and `on*` event handler
  attributes are analysed as text):
  - `html_smuggling` (critical): a Blob plus `createObjectURL` plus a download attribute, a
    decode step (`atob`, `Uint8Array`, `fromCharCode`) or an encoded payload of at least 200
    characters; or `msSaveOrOpenBlob`/`msSaveBlob` alone (they save the file themselves). A Blob
    with no path to a download is not flagged.
  - `credential_form_attachment` (high): any `<input type=password>`, or a form whose action is
    an absolute http(s) URL.
  - `svg_script` (high): an SVG with `<script>`, event handlers or `javascript:`.
  - `obfuscated_script` (medium): eval, unescape, `Function` constructor, `document.write`, long
    base64 (200+ characters) or long hex/percent-escape runs.
  - URLs: `href`, `src`, `action`, `data`, `xlink:href` and `formaction` attributes, meta
    refresh targets and `location`/`window.open` assignments in script (absolute http(s)/ftp
    only).
- Tests build PDFs with pypdf (JavaScript/OpenAction, a page `/AA` Launch action, an embedded
  file, a link annotation) and use fixture 10. The QR-in-PDF test is skipped without zbar.

## P6.5: Executables, shortcuts, images and YARA

- `phishlens/analyzers/binaries.py`: `analyze_pe`, `analyze_lnk`, `analyze_image` (same report
  shape as the other content analyzers) and `yara_scan`. The attachment analyzer routes by
  detected type: executable with an `MZ` header -> PE, `application/x-ms-shortcut` -> LNK,
  images -> QR. Tables live in `data/executable_indicators.yaml` (packer section names,
  entropy threshold 7.2, suspicious imports, LNK command patterns).
- PE (pefile, `fast_load` plus the import directory only): `pe_executable_attachment` (high)
  for every valid PE, with DLL flag, whether a signature is present (security directory size
  only; the signature is not validated), compile time (unusual before 2000 or in the future)
  and suspicious imports (A/W suffixes folded). `pe_packed` (medium) for a packer section name
  or a non-empty section with entropy of at least 7.2. An `MZ` file that pefile rejects gets no
  PE finding (P6.1 already flags it by type) and `pe.valid_pe = false`.
- LNK (LnkParse3): target (link info local base path, else common path suffix, else relative
  path), arguments, working dir, icon. `lnk_suspicious_command` (critical) when target or
  arguments contain a listed pattern (powershell, mshta, cmd /c, rundll32, regsvr32, wscript,
  cscript, certutil, bitsadmin, curl, UNC `\\`, http(s)://, msiexec, forfiles). URLs in the
  command become extracted URLs. Everything in evidence is defanged (`defang_text`).
- Images: `qr_code_url` (medium) when a QR code is decoded; URL payloads are defanged in the
  evidence and go to `extracted_urls` with source `qr_code`. Without zbar the image info records
  `qr_decoding: unavailable`.
- Inline images (`email.inline_images`) are now included as rows with `inline: true`, for YARA
  and QR only: no reputation lookups (logos would waste quota) and no filename findings. This
  is how fixture 12's QR image is reached. An email with only inline images is no longer
  `skipped`.
- YARA: every `*.yar`/`*.yara` in `YARA_RULES_DIR` (default `data/yara`) is compiled once
  (cached; `clear_yara_cache()` resets). Each file is test-compiled first, and one that fails is
  skipped and reported in `errors`, so a broken community file does not disable the rest. The
  external variables `filename`, `filepath`, `extension` and `filetype` are defined as empty
  strings for rules that use them. Scan timeout 10 s per file. Files that are
  `deep_analysis_skipped` are not scanned. One `yara_match` finding lists every hit (rule,
  namespace, tags, description, severity). Its severity is the worst `meta.severity` among the
  hits (default high).
- `data/yara/phishlens_example.yar` matches the harmless string `PHISHLENS-YARA-TEST-MARKER`,
  and `data/yara/README.md` explains adding YARA-Forge / signature-base / Elastic rules. The EICAR
  string is deliberately not used in a rule file, because desktop antivirus would quarantine it.
- Test samples: a minimal PE32 (headers plus one section of zeros or random bytes, no code) and
  a minimal LNK (header plus Unicode string data) are built in the tests. QR decoding on fixture
  12 needs zbar and is skipped without it; the QR path is also tested with a mocked decoder.

## P6.6: Sandbox gating and quarantine

- Sandbox choice: CAPE first (normally self-hosted), then Hybrid Analysis, whichever is
  configured (`_sandbox_client`). Hybrid Analysis still needs `UPLOAD_FILES_TO_HYBRID_ANALYSIS`
  (P4.5); otherwise its submit returns `not_configured`, which is recorded on the row.
- Gate, per file, in order. The first reason that applies is recorded as
  `row["sandbox"] = {"status": "skipped", "reason": ...}`: no sandbox configured, inline image,
  already known malicious, hash reputation already has a verdict (clean/suspicious), no
  high-risk type and no medium+ static finding, or the limit of 5 submissions per case
  (`MAX_SANDBOX_PER_CASE`, protects sandbox quota). "Hash reputation unknown" means the worst
  status was unknown, error or not_configured, or no lookup was made.
- Submit, then poll every `SANDBOX_POLL_SECONDS` (15) up to `SANDBOX_MAX_WAIT_SECONDS` (300). Waits
  go through `base._sleep`, so tests do not really wait. A timeout becomes a report with status
  `error`, and an entry in `errors`. Files are submitted one at a time (sandbox slots are
  limited).
- `sandbox_malicious` (critical) and `sandbox_suspicious` (medium) include the sandbox, score,
  first 20 signatures and the report link. A clean verdict is only stored on the row
  (`row["sandbox"]`, the full `SandboxReport`) and never removes static findings. Network
  domains, IPs, URLs and dropped hashes from finished reports are merged into
  `raw["sandbox_iocs"]` for IOC extraction (P9).
- Quarantine (`QUARANTINE_ENABLED`, `QUARANTINE_DIR`): every analyzed file, top-level,
  extracted or inline, goes into `<dir>/<case>/files.zip`, AES-encrypted with the password
  `infected`. Entries are named by SHA-256 (CLAUDE.md: generated names, never the attacker's
  file name), identical files are stored once, and `manifest.json` maps entries to original
  names, parents, types and hashes. The case key is the email's SHA-256 (or, for a
  `ParsedEmail` built without raw bytes, a hash of its attachment hashes), or the given
  `case_id` for file cases. `raw["quarantine_path"]` records the zip. `quarantine/` is gitignored.
  In tests the folder is a temporary directory (conftest).
- `analyze_files(files, case_id, passwords=None, reputation=True, sandbox=True)` runs the same
  stages without an email, for standalone file cases (P10). `analyze` and `analyze_files`
  share `_run`. `sandbox=False` together with `reputation=False` keeps everything on this host.

## P7.1: Hidden artifacts analyzer

- `phishlens/analyzers/artifacts.py` (module `artifacts`). The HTML body is parsed with
  BeautifulSoup and never rendered, so no remote images or pixels are loaded. Each check is its
  own step with its own error entry. Every URL in evidence is defanged, and text snippets are
  cut to 200 characters and defanged.
- Tracking pixels (`tracking_pixel`, low): only remote (http/https) images count, and only when
  1x1 or smaller (width and height attributes, `px` allowed) or hidden (their own style or an
  invisible ancestor). A long unique ID parameter (16+ characters) is recorded as an extra
  reason, but does not make an image a tracker on its own: CDN cache-busting parameters look
  the same. `cid:` inline images are ignored. Tracking hosts (defanged) go to
  `raw["tracking_domains"]`.
- Hidden text (`hidden_text`, medium): elements with display:none, visibility:hidden,
  font-size:0, opacity:0, (max-)height:0, the `hidden` attribute, or a text colour equal to the
  background colour (white text with no background counts as white-on-white). Only blocks of 10+
  characters count, and a hidden block inside another hidden block is counted once.
  `hidden_filler_text` (medium) when the hidden text totals 500+ characters.
  `zero_width_characters` (medium) for 3+ of U+200B/C/D, U+2060, U+FEFF, soft hyphen, U+180E.
- `text_html_mismatch` (low): both parts have at least 5 words and their word-set Jaccard overlap
  is under 0.2. The HTML side uses all of its text, hidden included (fixture 11 gives 0.23).
- Obfuscation: `encoded_link` (medium) for HTML entities inside an `href` (checked on the raw
  HTML, since the parser decodes them) or a query parameter that base64-decodes to an http(s) URL.
  The decoded URL goes to `extracted_urls` (source `artifact`). `script_in_body` (high) for any
  `<script>` in the body. `meta_refresh` (medium) for refresh targets, which go to
  `extracted_urls` (source `meta_refresh`).
- Headers: `missing_message_id` and `missing_date` (low). `date_in_future` (medium, more than 1
  day after delivery) and `date_too_old` (low, more than 30 days before delivery) are only
  checked when a Received timestamp exists; delivery is the newest one, so Date is never
  compared with itself. `message_id_domain_mismatch` (low) when the Message-ID's organizational
  domain differs from From's and is not a known ESP. The synthetic fixtures all use
  `@phishlens.test` Message-IDs, so it fires on them. `suspicious_mailer` (medium) when
  X-Mailer, User-Agent or X-MimeOLE matches a pattern in `data/suspicious_mailers.yaml`
  (validated regexes).
- Inline QR codes: decoded URLs go to `extracted_urls` (source `qr_code`) and
  `raw["inline_qr"]`, with no finding. The attachment analyzer already raises `qr_code_url`
  for the same image (P6.5), so the scorer does not count it twice; the pipeline deduplicates
  URLs.

## P8.1: Rule-based tone analysis

- `phishlens/analyzers/tone.py` (module `tone`), with lexicons in `data/lexicons/*.yaml`, one per
  category. Each file names its stable `finding_id` and its severity (`tone_urgency`,
  `tone_fear` and `tone_greed` medium; `tone_authority` and `generic_greeting` low;
  `credential_request` and `payment_request` high; `secrecy_request` medium), plus a `cap`,
  `phrases` and regex `patterns`. The loader validates severities and compiles every pattern.
  Each lexicon has a few Hindi (Devanagari) and Hinglish phrases.
- Text = subject + body (text part, or the HTML's visible text when there is no text part),
  normalized: zero-width characters removed, lowercased, runs of spaces collapsed, line breaks
  kept (so `^` patterns work per line, e.g. `Dear <email address>`).
- Phrases match as whole words with flexible whitespace. The word boundary includes the
  Devanagari block, because Python's `\w` does not cover Devanagari vowel signs. Within one
  category overlapping matches are resolved longest first, so "account will be suspended" beats
  "suspended". Categories may overlap each other (the same words can be urgent and fearful).
- One finding per category: `evidence.matches` (distinct phrases with a 40-character context
  snippet, defanged), `count`, `cap` and `counted = min(count, cap)`. `counted` is the per-category
  cap the scorer uses, so a very long message cannot pile up points in one category.
- `raw["normalized_text"]` (first 20,000 characters) and `raw["highlights"]`
  (`[category, phrase, start, end]` offsets into it) are for UI highlighting.
- Brands in the body: `domain.find_brand_mentions` on the body, then `domain.bind_identity`,
  using the header context for authentication and the domain context for lookalike/new domains.
  To avoid a second `brand_impersonation` for the same brand, brands the domain analyzer
  already claimed (`raw["identity"]["claimed_brands"]`) are skipped. Without a domain result,
  subject brands are checked here too. Findings from `bind_identity` are re-labelled with module
  `tone`. Body-only claims are weak (medium) unless the sender domain is a lookalike or new.

## P8.2: ML and LLM classifiers

- `phishlens/analyzers/tone_ml.py`: `ToneClassifier` protocol (`name`, `async classify(text)
  -> ToneScore(probability, rationale, details)`), `LocalTransformerClassifier` and
  `LLMClassifier`. `configured_classifiers()` returns only those that can run, so with nothing
  configured the tone analyzer records `raw["ml"] = {"status": "not_configured"}` and moves on.
  Both classifiers see `Subject: ...` plus the body in its original form (not the normalized
  rule text).
- Local model: enabled when `TONE_MODEL_PATH` is an existing folder and the optional `ml` extra
  (transformers, torch) is installed. It uses a cached `pipeline("text-classification",
  top_k=None, truncation=True)` in a worker thread. The phishing probability comes from a known
  phishing label (`LABEL_1`, `phishing`, `spam`, ...), else 1 - a known legitimate label's
  score (`LABEL_0`, `legitimate`, `ham`, ...). Unknown label names are an error rather than a
  guess. `ml_phishing_probability_high` when the probability is at least
  `ML_PHISHING_THRESHOLD` (0.8): high from 0.95, otherwise medium. The probability is in the
  evidence so the scorer (P10) can scale the weight by it.
- LLM: `phishlens/enrichment/llm.py` (external calls live in `enrichment/`), off unless
  `LLM_TONE_ENABLED=true` **and** `LLM_API_KEY` are set, because the email text leaves this host.
  It uses the official `anthropic` SDK (optional `llm` extra, imported only when used), in line
  with the SDK guidance, rather than the `BaseClient` httpx wrapper. The SDK does its own
  retries for 429/5xx and connection errors.
  - Model `LLM_MODEL`, default `claude-opus-5`. Request: `client.beta.messages.parse` with
    `output_format=LlmToneAssessment` (structured outputs, so the reply is schema-valid JSON,
    validated again by pydantic: urgency/greed/fear 0-10, impersonated_brand, requested_action,
    rationale). Server-side refusal fallbacks are on (`fallbacks="default"`, beta
    `server-side-fallback-2026-07-01`): phishing text may trip a safety classifier, and the API
    then reruns on a suitable model. A final `stop_reason == "refusal"` becomes an error with the
    category.
  - Prompt injection: the email goes inside `<email>` tags as untrusted data, and the system
    prompt says never to follow instructions in it.
  - An invalid answer is retried once (2 attempts). SDK errors are scrubbed of secrets. The text is
    cut to 50,000 characters, and that is recorded (`truncated`, `chars_sent`), never silent.
  - `LLMClassifier.probability` = the strongest of urgency/greed/fear / 10 (recorded, no
    threshold finding). `llm_impersonation` (medium) when the model names a brand and the sender
    is not that brand: a registry brand's legitimate domain, not free webmail, and not known to
    be unauthenticated. `raw["llm_warning"]` states that the text was sent to Anthropic.
- A failing classifier becomes an entry in `errors`; the rule layer's findings are unaffected.
  Tests use only fake classifiers, a fake pipeline and a fake Anthropic client.

## P8.3: Training script

- `scripts/train_tone_model.py`: the data preparation, stratified split and metrics are plain
  Python (unit-tested without ML libraries), and transformers/torch are imported only inside
  `train()`. A missing dependency exits with code 2 and an install hint; a bad CSV exits with
  code 1.
- Cleaning: HTML is stripped only when the text looks like HTML (so `5 < 6` survives),
  zero-width characters are removed and whitespace collapsed. Empty rows and exact duplicates
  after cleaning are dropped and counted. Labels other than 0/1 are an error, and the CSV must
  contain both classes.
- Split: per-class shuffle with a fixed seed (default 42); validation and test fractions of 0.1
  each by default, with at least one example per class in each split when a class has 3 or
  more examples. There is no scikit-learn dependency.
- Training: `AutoModelForSequenceClassification` with labels `legitimate`/`phishing` (which
  `LocalTransformerClassifier` recognises), a small in-script torch Dataset (no `datasets`
  dependency), evaluation every epoch, and the best epoch by validation F1 kept. Afterwards the
  model and tokenizer are saved to `--output` (default `models/tone`, gitignored), with
  `metrics.json` (test precision, recall, F1, accuracy, confusion matrix `[[TN, FP], [FN, TP]]`,
  split sizes, dropped counts, base model and parameters). The checkpoint folder is then removed.
- The `ml` extra now also includes `accelerate` (required by the Trainer).
- End-to-end run: done on a tiny synthetic CSV (40 harmless sentences) with
  `hf-internal-testing/tiny-random-DistilBertForSequenceClassification`. It trained, evaluated and
  saved, and the saved model loaded through `TONE_MODEL_PATH` in the tone analyzer. That tiny
  random model cannot learn, so its scores are meaningless; the real default is
  `distilbert-base-uncased` on a real dataset (`scripts/prepare_datasets.md`).

## P9.1: IOC extraction

- `phishlens/ioc/extract.py`: `extract_iocs(email | None, results) -> list[IOC]` (`None` for
  file cases). It reads only structured data from the analyzers (`raw` rows,
  `extracted_urls`, finding evidence for verdicts), so it depends on their field names rather
  than re-parsing anything.
- Sources and contexts: sender addresses and their domains (per role); Received hop IPs that
  are not private/reserved and not `TRUSTED_INTERNAL_HOSTS` (the originating one is labelled);
  email URLs, URL analyzer rows (and urlscan's final URL), every analyzer's `extracted_urls`
  (QR codes labelled), and each URL's host as a domain or IP; tracking-pixel domains; attachment
  names (the `safe_name` with bidirectional characters made visible) and hashes, including files
  unpacked from archives but not inline images; sandbox network domains, IPs and URLs, and
  dropped hashes. Our own defanged raw fields are turned back into values with `refang` (new in
  `ioc/defang.py`).
- Safety net: iocextract (refang on) runs only on genuine free text (text body, the HTML's text,
  model rationales) and only for URLs and IPv4. Its email extraction proved unreliable, and
  running it over our own evidence would harvest the legitimate brand domains we list there for
  comparison.
- Deduplication by `(type, value)` after normalization: domains, emails and hashes lowercased;
  URLs canonicalized (lowercase scheme and host, empty path -> "/", IPv6 brackets kept; path and
  query untouched). `source_module` and `context` are the merged, ordered, unique lists joined
  with ", " and "; " (the `IOC` model keeps them as strings). The verdict is the worst found:
  malicious > suspicious > clean > unknown (error/not_configured count as unknown).
- Verdicts:
  - URLs: the URL analyzer's `reputation_verdict`, else suspicious for strong static flags
    (link text mismatch, @ trick, brand lookalike, data/javascript URI, redirect to another
    domain, login page on an unrelated domain).
  - A URL's host inherits at most "suspicious" from a bad URL, since other pages on the same
    site may be fine.
  - Files and hashes: hash reputation, worsened by a finished sandbox verdict, else suspicious
    for strong static findings (type mismatch, double extension, RTLO, smuggling, macros,
    remote template, PDF launch/JS, LNK command, YARA, sandbox suspicious).
  - Sandbox network IOCs and dropped hashes: malicious when the detonation was malicious, else
    suspicious.
  - Sender addresses and domains: suspicious when a lookalike, brand-impersonation or young-
    domain finding names them. The Return-Path domain is suspicious when authentication passed
    only unaligned (spoofing).
  - IPs: unknown (no IP reputation lookup in the pipeline yet).
- Every IOC has a defanged form (`hxxp`, `[.]`, `[@]`); hashes and file names are unchanged.
  Output is sorted by type (URL, domain, IP, email, SHA-256, SHA-1, MD5, file name), then value.

## P9.2: IOC exporters

- `phishlens/ioc/export.py`: `to_csv` and `to_json` with the columns type, value, defanged,
  verdict, source, context. Both carry the raw value (for tools that import IOCs) and the
  defanged one (for people); the report/UI layers show the defanged column.
- `to_stix_bundle(iocs, report_name, others="observed"|"exclude", timestamp=None)` returns a
  `stix2.Bundle` (STIX 2.1):
  - one Identity ("PhishLens", `identity_class: system`) as `created_by_ref` of every object;
  - an Indicator per malicious or suspicious IOC. Patterns: `domain-name:value`,
    `ipv4-addr`/`ipv6-addr:value`, `url:value`, `email-addr:value`,
    `file:hashes.'MD5'|'SHA-1'|'SHA-256'`, `file:name`. Values are escaped for STIX string
    literals (backslash, quote). `indicator_types` is `malicious-activity` for malicious and
    `anomalous-activity` for suspicious; `labels` holds the verdict; names use the defanged
    value;
  - other IOCs (unknown/clean) as SCOs in one Observed Data object by default, or left out with
    `others="exclude"`. SCO ids are content-derived, so identical observables merge;
  - a Report (`threat-report`) referencing the indicators and the observed data. With nothing
    to reference, the bundle holds only the identity, because a STIX Report must reference at
    least one object.
- `timestamp` pins created/modified/valid_from/published for reproducible output (tests).
- Tests parse the bundle back with `stix2.parse(allow_custom=False)` and check every pattern with
  the official `stix2patterns` validator, which also checks hash formats.

## P9.3: MITRE ATT&CK mapping

- Rules live in `data/mitre_rules.yaml` (CLAUDE.md: tables in `data/`), loaded and validated by
  `phishlens/mapping/mitre.py`. A rule has technique IDs (checked for the `Txxxx(.yyy)` form) and
  exactly one condition: `any_of` (one finding is enough) or `all_of` (every item required; an
  inner list means "one of these", so "lookalike_domain + domain_age_under_30_days" also accepts
  the under-7-days finding). An optional `evidence` filter must match the finding's evidence, or
  one of its `files`/`urls` entries (case-insensitive), e.g. `high_risk_file_type` only for
  iso/img/vhd/vhdx -> T1553.005.
- `map_findings(findings)` returns one `MitreTechnique` per technique, sorted by ID, with
  `triggered_by` = the finding IDs that fired it across all rules. Names, tactics and URLs come
  from the local ATT&CK Enterprise data (mitreattack-python `MitreAttackData`, cached).
  Sub-technique names are shown as "Parent: Child". Without the data, the `techniques` fallback
  table in the YAML is used and URLs are built from the ID. Both forms use MITRE's URL format
  (no trailing slash).
- Beyond the plan's list: `sandbox_malicious`/`pdf_launch_action`/`lnk_suspicious_command`/
  `pe_executable_attachment` -> T1566.001 + T1204.002; `qr_code_url` -> T1566.002 + T1204.001;
  `llm_impersonation` -> impersonation; `encoded_link`, `hidden_text`,
  `zero_width_characters` -> T1027; `pe_packed` -> T1027.002; encrypted archive/Office findings
  -> T1027.013; `auth_but_unaligned`, `spf/dkim_pass_unaligned` and
  `forged_auth_results_header` -> T1566.
- Checking against the current ATT&CK data (downloaded with `scripts/update_attack_data.py`)
  showed two changes since the plan was written:
  - **T1656 Impersonation is revoked** and replaced by **T1684.001 "Social Engineering:
    Impersonation"**. The plan's `brand_impersonation, display_name_brand_spoof -> T1656` rule
    therefore maps to T1684.001 (commented in the YAML).
  - ATT&CK split the old `defense-evasion` tactic: these techniques now fall under `stealth`
    (T1027.*, T1036.*, T1221, T1684.001), and T1553.005 under `defense-impairment`. The fallback
    table matches the data.
  A test fails if a rule names a missing or revoked technique, or if a fallback name or tactic
  differs from the data. It is skipped when the data has not been downloaded.
- `scripts/update_attack_data.py` streams the file to `.part`, checks that it is a STIX bundle,
  then replaces the old file.

## P10.1: Scoring engine

Plan reviewed and approved before building.

- `data/weights.yaml` (CLAUDE.md lists weights among the `data/` files) holds: an explicit
  weight for all 101 finding IDs (a test fails when an analyzer produces an unweighted ID); a
  severity fallback (info 0, low 5, medium 15, high 30, critical 50); module caps (attachments
  70, header 60, urls 60, domain 50, tone 30, artifacts 25); thresholds; overrides; and
  confidence settings. `phishlens/scoring/weights.py` validates it: all five severities in the
  fallback, known severities in per-severity weight maps, `0 < suspicious < malicious <= 100`,
  exactly one condition per override.
- A weight can be a per-severity map (for example `brand_impersonation: {critical: 50, high:
  35, medium: 15}`) for findings whose severity varies. A severity missing from the map uses the
  fallback.
- `finding_points` scaling: tone findings get weight x (0.5 + 0.5 x counted/cap), so one phrase
  earns 60% and a full category 100%; `evidence.probability` (the ML finding) multiplies the
  weight; findings downgraded by a trusted ARC forward (`evidence.downgraded_by`) score at the
  severity fallback of their new severity (low = 5). That is how `arc_trusted_forward` reduces
  header penalties.
- Findings are grouped per ID in the analyzers (one finding per kind of problem), so scores do
  not grow with the number of URLs or files.
- `RuleScorer.score(results, case_type)`: module points capped, total clamped 0-100. Labels:
  email clean < 30 <= suspicious < 60 <= malicious; file clean < 20 <= suspicious < 50 <=
  malicious (thresholds inclusive). `Finding.score` of every finding is set to its (uncapped)
  contribution. `top_findings` holds the 5 largest positive contributors.
- Overrides: `attachment_known_malicious`, `url_known_malicious`, `sandbox_malicious`,
  `html_smuggling` -> malicious; `auth_but_unaligned` + `brand_impersonation` -> malicious;
  any critical finding -> at least suspicious. An override never lowers a label, raises the
  score to at least the forced label's threshold, and is listed in `overrides_applied`
  (including when it did not change the label).
- Confidence = share of analyzers that ran without errors (skipped ones do not count; 1.0 when
  none ran), minus 0.1 per unconfigured key service (VirusTotal, Safe Browsing, abuse.ch),
  with the penalty capped at 0.3 and a floor of 0.1.
- `Scorer` protocol and `get_scorer()` (`SCORER=rule|ml`). `MLScorer` loads a joblib bundle
  `{"model", "features"}` from `SCORER_MODEL_PATH`. The model's probability x 100 replaces
  the total score, the label is recomputed, and overrides still apply. Without a model (or
  without scikit-learn/joblib) it returns the rule verdict with
  `ml_scorer_unavailable_used_rules` in `overrides_applied`. scikit-learn is not a dependency;
  it is only needed by whoever trains such a model.
- `phishlens/scoring/features.py`: a stable column list (every weighted finding ID, then
  `module:<name>`), with values in points. `scripts/export_features.py` writes one CSV row per
  saved `AnalysisReport` (reports that are not AnalysisReports are skipped). Labels come from a
  `case_id,label` CSV, or with `--use-verdict` from the report's own verdict (weak labels,
  documented as such).
- The initial weights are a first calibration. P10.2 checks every fixture against
  `tests/fixtures/labels.yaml` and adjusts weights if needed.

## P10.2: Email pipeline orchestrator

- `phishlens/pipeline.py`: `analyze_email(raw_bytes, progress_cb=None, *, network=True,
  case_id=None) -> AnalysisReport`. The case ID is a random UUID (hex) unless given.
- Order: header first; then concurrently [domain -> tone], artifacts and attachments. Tone
  runs after domain (a deviation from the plan's "all four concurrently") because it skips
  brands the domain analyzer already reported, so each brand gives one `brand_impersonation`.
  Then urls with `email.urls` plus attachment and artifact `extracted_urls`. Each analyzer gets
  a `context` dict with the results so far.
- `run_analyzer`: `asyncio.wait_for` with `ANALYZER_TIMEOUT_SECONDS` (120), or
  `ATTACHMENT_TIMEOUT_SECONDS` (900, it may wait for a sandbox). A timeout or exception becomes
  an `AnalyzerResult` with only an error, which lowers confidence and does not stop the
  pipeline. `progress_cb(module, status)` may be a function or a coroutine and gets `pending`
  (all modules first), `running`, `done` or `error`, plus `nested` and `scoring`. A failing
  progress callback is ignored.
- Nested emails (`message/rfc822`, up to `NESTED_EMAIL_MAX_DEPTH` = 2): each is analyzed with
  the same pipeline (no progress events). Their findings are copied into a `nested` result
  with `module = "nested.<analyzer>"` and `evidence["nested"] = "nested:<n>"`, so a forwarded
  phishing mail counts toward the verdict. It has its own module cap (60 in `weights.yaml`).
  `raw["emails"]` lists subject/from/errors per nested mail. Nested IOCs are merged into the
  case's IOCs (`merge_iocs`: same type+value merges sources/contexts, worst verdict wins).
- After scoring, the MITRE mapping writes technique IDs into each triggering finding's `mitre`
  list, so reports can show them per finding.
- Offline mode (`network=False`, used by the CLI's `--no-network`):
  `phishlens/enrichment/network.py` holds a context variable that every DNS lookup (error
  `offline`), enrichment/sandbox client (`not_configured`, reason "network disabled"), RDAP
  (`skipped`) and the LLM respect. The analyzers treat it as skipped, not as an error: the
  header records SPF `skipped_reason: offline`, the domain analyzer skips MX. The pipeline also
  turns off hash/URL reputation and the sandbox. `services_used` is then empty.
- `services_used` / `services_not_configured` come from `Settings.configured_services()`
  (names only, never keys).
- Calibration against `tests/fixtures/labels.yaml`: with the fake internet (each fixture's
  sender domain publishes SPF for its sending IP, as its Authentication-Results header says;
  microsoft.com and paypal.com publish DMARC reject; MalwareBazaar knows EICAR), every fixture
  gets its expected verdict. One weight changed: `hidden_text` 15 -> 25, because text hidden
  to fool filters is deliberate evasion and fixture 11 (suspicious) scored only 22 before.
  `qr_code.eml` needs zbar to be judged and is skipped without it.

## P10.3: Standalone file pipeline

- `analyze_file(raw_bytes, filename, progress_cb=None, *, network=True, case_id=None)`: the file
  becomes one `Attachment` (hashes computed by `make_attachment`), then
  `attachments.analyze_files([file], case_id)` (unpacking, reputation, content, sandbox,
  quarantine under the case ID), then the URL analyzer on the URLs found inside the file (with
  an empty `ParsedEmail`), then IOCs (`extract_iocs(None, ...)`), MITRE and scoring with
  `case_type="file"` (thresholds 20/50).
- header, domain, tone and artifacts get `skipped=True` results with `raw = {"skipped_reason":
  "not an email"}`. Progress reports them as `skipped`, and they do not lower confidence.
  `report.file_info` is the file with its detected type (no bytes are serialized).
- `analyze_input(raw_bytes, filename)` uses `ingest.load_input` (content detection, not the
  extension). Emails, including `.msg` converted to RFC 822, go to `analyze_email`; everything
  else to `analyze_file`. Oversize input or a broken `.msg` raises `LoaderError` before any
  analysis. The CLI/API turn that into a user-facing error.
- The email and file pipelines share `run_analyzer` (timeouts, error results) and `build_report`
  (MITRE tagging, scoring, services).

## P11.2: Executive summary and recommendations

- `phishlens/reporting/summary.py`, no LLM. `build_summary(report)` returns 3-5 sentences: a
  verdict sentence (label, score, confidence; for Clean also "no significant indicators", and
  then nothing else), then up to four evidence sentences. Findings are taken in order of points,
  one sentence per finding ID from the `TEMPLATES` table, filled with the real evidence: brand,
  the domain that actually authenticated, domain age from RDAP when known, lookalike target and
  technique, display name vs address, link text vs destination, reputation services, malware
  families, file names, quoted tone phrases. When fewer than 3 sentences result, a closing
  sentence points to the details. Every sentence is defanged, so it is safe in the CLI, the API
  and reports; this also defangs file names that are valid domains (`eicar[.]com`).
- De-duplication: `auth_but_unaligned` gets no sentence of its own when `brand_impersonation`
  is present, because the brand sentence already names the authenticated domain ("claims to
  be from Microsoft, but it was authenticated by zetatech.xyz, not by microsoft.com").
- `build_recommendations(report)`: nothing for Clean (the report shows "No action needed.").
  - Suspicious: do not click or open until verified; confirm with the sender through a known
    channel (emails).
  - Malicious: block the indicators (with the count) and, for emails, the sender domain;
    search and remove the message from all mailboxes. When the From domain belongs to a real
    brand (a forged `microsoft.com`), the sender domain is not to be blocked, and an explicit
    "do not block <domain> itself" line says why.
  - By findings: credential reset / session revoke / MFA and forwarding-rule check when there
    are links and the case is malicious or asks for credentials; isolate the host and run an EDR
    scan when a risky attachment was found; no payment or bank-detail change for payment
    requests; report to the impersonated brand(s); report malicious links to Safe Browsing and
    the host's abuse contact; thank the user who reported it (emails).
- `render_html` fills both by default, and the CLI summary panel shows the evidence sentences.
- Tests: fixtures 2, 6 and 14 in the fake internet (the `world` fixture now lives in
  `tests/conftest.py`) mention the key evidence, and recommendations fit each case.

## P12.1: Database models

- `api/db.py` (SQLModel): one table, `Case`. The ID is a short readable string
  `PL-YYYYMMDD-XXXXX` (5 random characters from an alphabet without 0/O/1/I/L), safe in URLs
  and file names, and also used as the pipeline `case_id`, so reports, quarantine folder and row
  share it. Other fields: created/updated timestamps, case type, original file name, input
  SHA-256 (indexed, for deduplication), subject, sender, verdict, score, confidence, status
  (queued/running/done/error, validated), error message, report JSON path, and `report_files`
  (format -> path, a JSON column). The full report stays in its JSON file; the row holds only
  what listing, searching and statistics need.
- Engine per database URL (cached). SQLite gets `check_same_thread=False` (the worker and the
  API use threads), and in-memory SQLite a `StaticPool`, so tests share one database. Postgres
  works through `DATABASE_URL` with `pool_pre_ping`. `init_db` creates tables (called on API
  startup). `session_scope` commits on success and rolls back on errors.
- Helpers: `create_case`, `get_case`, `update_case` (rejects unknown fields and invalid
  statuses, bumps `updated_at`), `delete_case` (returns the row so the caller can remove its
  files), `find_completed_by_sha256` (newest finished case, for P12.4), and `list_cases`
  (filters verdict / case_type / date range / q, which searches subject, sender and file name
  case-insensitively; newest first; offset/limit capped at 500; returns items and total).
- SQLite stores datetimes without a timezone; they are written in UTC.

## P12.2: Job queue and progress

- `api/worker.py`. Uploads are stored at `<QUARANTINE_DIR>/uploads/<case_id>/input.bin`: a
  generated name, never the uploader's file name, and never in a served folder. Reports go to
  `<REPORTS_DIR>/<case_id>/` (new setting, default `reports`, gitignored); they are downloaded
  through the API, not served statically.
- `run_analysis(case_id, stored_input_path, filename, mode)` is the job. Modes: `auto`
  (`analyze_input`, routes by content), `file` (`analyze_file`) and `email` (`analyze_email`,
  for pasted source). The pipeline gets the DB case ID. Per-module progress is written through
  the pipeline's progress callback, plus a `job` entry (running/done/error). Every format is
  generated. The Case row gets status, verdict, score, confidence, case type, subject, sender,
  `report_files` and `report_json_path`.
- Failures: loader errors, missing files, disk errors and anything unexpected set status `error`
  with a message (up to 2000 characters). When the analysis itself finished but report writing
  failed, a partial JSON + HTML is still attempted and the verdict recorded.
- Progress store: `RedisProgressStore` (hash `progress:<case_id>`, expires after 7 days) or
  `MemoryProgressStore` (thread-safe; tests and sync mode).
- Queues: `RQQueue` (queue `phishlens`, job ID `analysis-<case_id>`, 1 h timeout; run workers
  with `rq worker phishlens`) and `SyncQueue` (runs the job at once in the calling thread). A new
  setting `JOB_QUEUE=rq|sync` picks one; sync also lets the API run without Redis for local use.
  `healthy()` reports Redis reachability and the number of RQ workers for `/api/health`.
- `fakeredis` is a new dev dependency to test the Redis store without a server. The worker tests
  run real jobs through `SyncQueue` in the fake internet with a temporary SQLite database.

## P12.3: API endpoints

- `api/main.py` (`create_app()`, module-level `app` for `uvicorn api.main:app`). Tables are
  created at startup (lifespan).
- Uploads: read in 1 MB chunks and refused with 413 above `MAX_INPUT_SIZE_MB`; empty uploads
  get 400. `/api/analyze` checks the content with `load_input`: anything that is not an email
  (.eml, or Outlook .msg converted) is refused with a message pointing to `/api/analyze-file`.
  `/api/analyze-file` accepts several files; each becomes its own file case (mode `file`).
  `/api/analyze-raw` takes `{raw_source}` and refuses text without an RFC 822 header block.
  All return 202 with the case ID(s).
- Starting a case: create the row, store the upload under a generated name, record its SHA-256,
  set progress `job: queued`, then enqueue (RQ), or with `JOB_QUEUE=sync` add a FastAPI
  background task, so the request returns at once and the job runs in a worker thread.
- Display file names are sanitized (base name only, printable characters, 200 max); stored
  files never use them.
- `GET /cases/{id}` returns the report JSON with every string and every dict key defanged
  (`_defang_tree`), because the report has domain names as keys (for example lookalike
  matches). CLAUDE.md: API responses carry no live indicators. It returns 409 while the case is
  queued/running and 404 when no report exists. Listings defang subject and sender too. The
  downloadable JSON/CSV/STIX report files keep raw values for analyst tooling (the CSV also has a
  defanged column). Downloads are always `Content-Disposition: attachment`, so a report is never
  rendered by the API origin, and only generated report files can be downloaded.
- `GET /cases`: filters verdict / case_type / date_from / date_to / q, page + page_size (max
  200), newest first. `GET /stats`: total, counts per verdict (running cases as "pending"),
  error count, and cases per day for the last 30 days (UTC dates, the same as stored timestamps).
- `DELETE /cases/{id}`: removes the row, `reports/<id>/`, the stored upload,
  `quarantine/<id>/` and nested-email quarantine folders (`<id>_nested*`), and the progress
  entry.
- `GET /health`: version, queue health (Redis reachable, worker count, or sync),
  `configured_services()` (true/false only) and the supported report formats.
- Related fix: the attachment quarantine was keyed by the email's SHA-256, so an API delete could
  not find it. `attachments.analyze` now takes `case_id`, the pipeline passes it (nested emails
  use `<case_id>_nested<n>`), and CLI and API cases are quarantined under their own case ID.

## P12.4: Security and deduplication

- `api/security.py`. `require_api_key` is an app-wide dependency: every endpoint except
  `/api/health` needs `X-API-Key` equal to `PHISHLENS_API_KEY` (constant-time comparison);
  otherwise 401 with `WWW-Authenticate: X-API-Key`. With no key configured, authentication is
  off (the existing "local use" mode from config). `/api/health` reports `auth: api_key|disabled`
  so this is visible.
- CORS: `CORS_ORIGINS` (default `http://localhost:8501`, the Streamlit UI), with methods
  GET/POST/DELETE and headers X-API-Key/Content-Type. Other origins get no CORS headers.
- Deduplication: before creating a case, the SHA-256 of the input is looked up among finished
  (`done`) cases *of the same case type* (the same bytes analyzed as a file and as an email are
  different analyses). A match returns that case with `duplicate: true`; `?force=true` on the
  three upload endpoints re-analyzes. Failed cases are never reused. Pasted source counts as the
  same input when its bytes match an upload.
- Upload rate limit: `UPLOAD_RATE_LIMIT=count/seconds` (default 20/60; `0/...` turns it off),
  a thread-safe sliding window per client IP in memory (per API process), on the three upload
  endpoints only. Over the limit: 429 with `Retry-After`. Behind a reverse proxy the client IP
  is the proxy unless uvicorn runs with `--proxy-headers`/`--forwarded-allow-ips` (to document
  in P15).
- File names: sanitized for display (P12.3); stored files always use generated names.
- Quarantined inputs are never returned: downloads must resolve inside `REPORTS_DIR` (a tampered
  `report_files` entry pointing at the quarantine gives 404), and no endpoint reads upload
  contents back.

## P13.1: UI foundation

- The UI (`ui/`, Streamlit 1.64) talks only to the API through `ui/api_client.py`. It imports
  nothing from the analysis code and never analyzes. Base URL `PHISHLENS_API_URL` (default
  `http://localhost:8000`) and `PHISHLENS_API_KEY` (sent as `X-API-Key`) come from the
  environment.
- `api_client` is a typed function per endpoint over httpx (30 s timeouts, 300 s for uploads).
  Every failure becomes `ApiError` with an actionable message: backend unreachable (with the
  uvicorn command), timeout, 401 (set PHISHLENS_API_KEY), 413 (the backend's size message),
  429 (wait N seconds from Retry-After), 404 and validation errors (the backend's detail).
  Empty/"All" filters are left out of list queries.
- `ui/theme.py` defines the verdict colors (green Clean, amber Suspicious, red Malicious, grey
  unknown) and severity colors once, plus `verdict_badge`, `score_gauge` (a 0-100 bar in the
  verdict color), `severity_pill`, `status_dot` and `defanged_code` (`st.code`, which has a copy
  button). The small HTML they emit is built from `html.escape`d values; nothing from an email
  or attachment is ever rendered as HTML (the API content is defanged text).
- `.streamlit/config.toml`: light professional theme in the report's colors, headless, 25 MB
  upload limit (the API default), XSRF protection on, no usage statistics.
- `ui/app.py` uses `st.navigation` with pages Analyze (default), Case view (`/case`), History and
  Settings. The sidebar shows the PhishLens name, a backend status dot from `/api/health`
  (cached 10 s), a warning when the job queue's Redis is down, and the API URL. The pages are
  filled in P13.2-P13.4.
- Tests: the client with respx (every endpoint, the key header, each friendly error, backend
  down) and the app with Streamlit's `AppTest` (backend online, down, Redis down). A manual smoke
  run started the real API (`JOB_QUEUE=sync`) and UI servers; both answered their health checks.

## P13.2: Analyze page

- Three tabs as planned. "Analyze email": uploader restricted to .eml/.msg (the API checks the
  content anyway), plus the "How do I get the email file?" expander (Gmail, Outlook desktop,
  Outlook on the web, Thunderbird; screenshots, PDFs and copied text do not work; forwarding
  loses headers). "Analyze file": multiple files of any type, with the plan's note. "Paste email
  source": a text area with hints for Gmail "Show original".
- An "Analyze again" toggle sends `force=true` (P12.4 deduplication). When the API answers
  `duplicate: true` the page says the input was already analyzed and shows that case.
- Progress logic is in `ui/progress.py` (pure functions, unit-tested). `steps(status)` maps
  the API's per-module progress onto the 11 steps the plan lists: Parsing (done once any module
  started), Header ... Hidden artifacts (the module states), IOCs and MITRE mapping (done once
  scoring started), Scoring, Report (done when the case is done). Each step is pending, running,
  done, error or skipped (the email-only modules in file cases). `poll(case_ids, get_status,
  render)` refreshes every unfinished case once a second until all are done/error (30 min cap).
  Its sleep goes through a module hook (`progress._sleep`) so tests never patch `time.sleep`
  globally, which breaks Streamlit's AppTest.
- Each submitted case gets its own bordered progress card, redrawn in place, with the step icons
  and the final verdict or error. A single finished case opens the Case view
  (`st.switch_page(..., query_params={"id": case_id})`, and `session_state["case_id"]`);
  several cases show an "Open" button each.
- API errors (too large, not an email, rate limited, backend down) are shown as they come from
  `ApiError`.
- AppTest cannot drive file uploads, so the flow is tested end to end through the paste tab
  (input, submit, two polls, switch to the case), and the upload tabs share the same code path.

## P13.3: Case view page

- **Summary and recommendations come from the API.** `GET /api/cases/{id}` adds `summary` and
  `recommendations`, built with `phishlens.reporting.summary` like the HTML report, so the UI
  never imports analysis code. If an old report JSON no longer validates, both are empty lists.
- **Pure helpers in `ui/case_data.py`.** Everything that turns report JSON into rows, trees and
  groups lives there and is unit-tested; `ui/pages/case_view.py` only lays it out.
- **Body highlights are re-found, not taken from offsets.** The API defangs `normalized_text` and
  the highlight phrases, so the analyzer's character offsets no longer line up. Phrases are found
  again in order (case-insensitive); a phrase that can no longer be found is skipped.
- **Only two kinds of live links.** MITRE technique links (`https://attack.mitre.org/...`) and
  urlscan.io screenshots (loaded with `st.image`) are re-fanged, and only after checking the
  host prefix. Every other value stays defanged. Email and attachment content is never rendered;
  the Body tab shows the sanitized, escaped text.
- **Downloads are lazy.** Each download button gets a callable, so a report format is fetched
  from the API only when its button is clicked. File names are `<case_id>_<verdict>.<ext>`
  (`.stix.json` for STIX).
- **File cases** hide the Headers, Sender & domain, Body and Artifacts tabs and say why.
- **Cases that are not finished** (queued/running) show their status and a Refresh button
  instead of a partial report. A failed case that still has a verdict shows the report with a
  warning.

## P13.4: History and Settings pages

- **The API gained two read-only fields.** `/api/stats` `per_day` entries now also count each
  verdict (`clean`, `suspicious`, `malicious`, `pending`, `error`) so the History chart can stack
  verdicts over 30 days. `/api/health` has a `config` block with the verdict thresholds (from
  `data/weights.yaml`), scorer, VirusTotal and ML thresholds and the upload/LLM switches, so the
  Settings page shows the backend's real configuration. No secret is ever part of it.
- **Settings is read-only.** Configuration lives in the backend's environment / `.env`; the UI
  only displays it. Service names, purposes, setting names and sign-up links are in
  `ui/services.yaml` (a test keeps it in sync with `SERVICE_FIELDS`). Sign-up links are the
  project's own static links, not analyzed values, so they are clickable.
- **Opening and deleting cases.** The table has a relative `Open` link per row (`case?id=...`)
  and, for keyboard use and testability, a case picker with *Open case* / *Delete case* buttons.
  Delete asks for confirmation inline (a warning with *Yes, delete* / *Cancel*) rather than a
  modal dialog.
- **Paging.** 25 cases per page; any filter change goes back to page 1, and a page that no
  longer exists (after deletions) falls back to the last page.
- `use_container_width` is deprecated in Streamlit 1.64; the UI uses `width="stretch"`.
